# 트렌드 수집 엔진과 추천 알고리즘 평가 (2026-11-19)

코드(`lib/ingest/trends.ts`, `lib/ingest/trend-builder.ts`, `lib/ingest/external-trends.ts`, `lib/recommendations.ts`, `lib/personal.ts`)를 읽고, 로컬(3001)에서 실제 데이터로 `/trends`, `/news`, 홈 화면을 확인한 결과입니다. 숫자는 2026-11-19 화면 기준입니다.

## 요약

| | 지금 상태 | 가장 큰 문제 | 먼저 할 일 |
|---|---|---|---|
| 트렌드 엔진 | 매일 1번(06:00 KST) 수집, 미리 정한 이름 목록에 걸리는 글을 세어 점수화 | **새 트렌드를 찾지 못함.** 정해 둔 이름(정규식 약 40개, 도구 이름 목록, 빌드 아이디어 11개) 안에서만 순위가 바뀜 | 지난 실행의 행 정리, 가짜 지표(성장률, 막대) 제거 |
| 추천 | 관심 분야, 킵, 좋아요 태그를 글 태그와 겹쳐 세고 편집 점수를 더함 | **개인화가 약함.** 관심사 하나 일치는 +4점인데 편집, 최신성 점수가 40점 넘게 깔려서 사람마다 순서가 거의 같음 | 개인 신호와 편집 점수를 분리해 섞기, 클릭 기록으로 측정 시작 |

## 1. 트렌드 수집 엔진

### 어떻게 돌아가나
1. `scheduled-ingest.yml`이 매일 21:00 UTC에 수집 단계를 차례로 부름. `external-trends`(HN, dev.to, Stack Overflow, npm, Hugging Face, RSS) 다음에 `trends`.
2. `trends`는 최근 글 220개, AI 제품 140개, 스타 많은 저장소 180개, 논문 120개를 읽음.
3. 각 글의 제목과 태그에 **미리 정한 정규식과 이름 목록**을 대어 걸리면 "신호" 1개를 만듦(`addWorkflowSignals`, `addImplementationPatternSignals`, `addKnownToolModelSignals`, `extractBuildIdeas`).
4. 최근 30일 신호를 이름별로 묶고, 점수 = 신호 세기 + 최근 7일 출처 수 + 출처 종류 수 + 출처 개수 + 성장 + GitHub/PH 가산(`buildTrendCandidates`).
5. 분류마다 상위 30개를 `trends` 표에 `keyword` 기준으로 덮어쓰고, 오늘 점수를 `trend_snapshots`에 남김.

### 실제 데이터로 본 것
- 화면의 주제 **180개** 가운데 AI 도구·모델이 **126개(70%)**, 빌드 아이디어는 **0개**.
- 한 번 실행에 분류당 30개, 최대 150개만 쓰는데 180개가 보임. **지난 실행의 행이 지워지지 않고 쌓임**(아래 2번).
- AI 도구·모델 상위권에 `cli`, `core`, `mcp-server`, `observability` 같은 **npm 패키지 일반 이름**이 트렌드로 올라옴.
- 1위부터 10위까지가 `MCP Server Design`, `Eval Pipeline`, `LLM Observability`처럼 코드에 적어 둔 패턴 이름 그대로.

### 문제 (중요한 순서)
1. **새로운 것을 발견하지 못함.** 신호는 코드에 적힌 이름에 걸려야만 생김. 지난주에 처음 나온 도구나 패턴은 목록에 추가하기 전까지 트렌드가 될 수 없음. "트렌드"라기보다 "정해 둔 주제의 언급량 순위"에 가까움.
2. **지난 행이 남음.** `trends`는 `keyword`로 upsert만 하고 지우지 않음. 화면(`loadTrends`)은 `rank` 순 180개를 그대로 읽어서, 오늘 순위에서 빠진 주제도 예전 순위 번호를 달고 섞여 나옴.
3. **가짜 지표.**
   - `weekly_growth_rate`: 이전 7일 출처가 없으면 무조건 100. 읽는 범위(최근 30일, 표마다 상위 N개)가 좁아 이전 구간이 거의 비고, 결과적으로 거의 모든 주제가 `new`, 100%. 문구 "최근 7일 관심도가 100% 상승"은 근거가 없음.
   - `bars`: 오늘 점수에 고정 비율(0.42~1)을 곱한 값이라 추세가 아님. 화면에서는 이미 안 씀.
4. **점수가 날마다 상대값.** `display_score = 원점수 / 그날 최고점 × 100`, 최소 25. 그날 1위가 약하면 모두 올라가고 강하면 모두 내려감. 트렌드 화면의 "▲44" 같은 변화량은 실제 관심 변화가 아니라 기준점 변화일 수 있음.
5. **저장소 쪽 치우침.** 저장소는 `stars` 순 상위 180개를 읽음. 오래된 유명 저장소가 매번 들어오고, `pushed_at`(아무 커밋)을 날짜로 써서 "최근" 신호로 셈. 한 글이 여러 정규식에 걸리면 신호가 여러 개 생겨 같은 글이 여러 주제를 동시에 밀어 올림.
6. **빌드 아이디어 분류가 죽어 있음.** 고정 아이디어 11개 중 하나여야 하고 출처 2곳, 종류 2개를 넘어야 하는데 오늘 0개.
7. **일반어 필터 구멍.** `GENERIC` 목록이 `external-trends.ts`와 `trend-builder.ts`에 따로 있고 내용이 다름. npm 패키지 이름(`cli`, `core`)은 둘 다 통과.

### 개선안
| 순서 | 할 일 | 크기 |
|---|---|---|
| 1 | 실행이 끝나면 이번에 안 쓴 `trends` 행을 지우거나 `active=false`로. 화면은 `updated_at`이 오늘인 행만 | 작음 |
| 2 | `weekly_growth_rate`, `trend_direction`, `bars`, "100% 상승" 문구를 쓰지 않음. 변화는 `trend_snapshots`의 원점수로만 | 작음 |
| 3 | 스냅샷에 `raw_score`도 저장해 날짜 간 비교를 원점수로 | 작음 |
| 4 | 일반어 목록 하나로 합치고 npm 패키지명은 스코프 포함 이름만 허용 | 작음 |
| 5 | 저장소는 `stars_delta_7d` 순으로 읽고 날짜는 첫 수집일 기준 | 중간 |
| 6 | **발견 단계 추가**: 고정 목록 밖의 이름을 후보로 뽑기(제목의 고유명사, 저장소 이름, 패키지 이름을 2곳 이상에서 봤을 때). 기존 목록은 이름 정리용으로만 | 큼 |
| 7 | 빌드 아이디어 분류는 고정 문자열 대신 인사이트의 검증된 문제와 연결하거나 분류에서 빼기 | 중간 |

## 2. 추천 알고리즘

### 어떻게 돌아가나
추천은 두 갈래입니다.
- **규칙 추천** `ruleReads` → `scoreNewsletterItems`: 아티클 "나에게 맞는" 탭, 이번에 바꾼 아티클/홈 배너가 씀. 관심 분야, 목표, 스택, 킵한 글의 태그, 좋아요한 글의 태그를 글의 태그와 겹쳐 세고 편집 점수(우선순위, 새로움, 출처 품질)와 최신성을 더함. 킵하거나 싫어요한 글은 빠짐.
- **임베딩 추천** `forYou` → `embeddedPicks`: 홈 "나를 위한 추천"이 씀. 관심사, 킵한 제목, PRD 제목을 한 문장으로 만들어 임베딩하고 비슷한 문제와 콘텐츠를 찾음. 실패하면 규칙 추천으로.

### 점수 구조에서 보이는 것
`scoreContent`의 대략적인 범위:

| 항목 | 점수 |
|---|---|
| 관심 분야 태그 1개 일치 | +4 |
| 스택 1개 일치 | +3 |
| 좋아요/킵 태그 일치 | 최대 +9 |
| 편집 우선순위 × 0.2 | 최대 +20 |
| 새로움 × 0.1 + 출처 품질 × 0.1 | 최대 +20 |
| 최신성 / 5 | 최대 +7 |

개인 신호가 1~2개 맞아도 +4~8점인데, 편집, 최신성 점수가 모든 사람에게 같은 값으로 30~47점 깔립니다. 그래서 **누가 보든 상위 글이 거의 같습니다.**

### 문제 (중요한 순서)
1. **개인화가 편집 점수에 묻힘.** 위 표 그대로. 관심사가 다른 두 사람의 1순위가 같을 가능성이 큼.
2. **"나에게 맞는 글"이라는 표시가 틀릴 수 있음(이번 작업에서 생긴 문제).** 관심 분야도 킵도 없는 사람에게도 배너가 "나에게 맞는 글, 프로젝트로 확장 가능"으로 나옴. 이 이유는 글의 성질이지 사람과 맞아서가 아님. 바로 고침(아래).
3. **두 추천이 서로 다른 순서를 냄.** 홈 아래 "나를 위한 추천"(임베딩)과 홈 위 배너(규칙)가 다른 엔진이라 같은 화면에서 1순위가 다를 수 있음.
4. **글자 부분 일치의 오탐.** `fuzzyMatch`는 4자 이상이면 포함 관계로 맞춤. `java`가 `javascript`, `react`가 `reaction`에 맞음.
5. **측정이 없음.** 추천을 눌렀는지, 배너를 본 뒤 읽었는지 기록이 없어 잘 맞는지 판단할 근거가 없음. `content_reactions`(좋아요/싫어요)와 조회수만 있음.
6. **싫어요가 주제에는 반영 안 됨.** 싫어요한 글 하나만 빠지고, 그 주제는 계속 올라옴.

### 개선안
| 순서 | 할 일 | 크기 |
|---|---|---|
| 1 | 배너 표시: 관심 분야나 킵/좋아요가 있을 때만 "나에게 맞는 글"과 개인 이유, 없으면 "오늘의 추천" | 작음(이번에 함) |
| 2 | 점수를 `개인 점수`와 `편집 점수`로 나누고, 개인 신호가 있는 사람은 개인 점수 순으로 먼저 고른 뒤 편집 점수로 동점 정리 | 작음 |
| 3 | 배너와 "나를 위한 추천"이 같은 엔진(임베딩 우선, 실패 시 규칙)을 쓰게 | 중간 |
| 4 | 짧은 영어 단어뿐 아니라 모든 태그를 단어 단위로 맞춤 | 작음 |
| 5 | 추천 노출과 클릭을 `content_reactions`처럼 기록(`recommendation_events`). 주간 지표: 배너 클릭률, 추천 글 킵 비율 | 중간 |
| 6 | 싫어요한 글의 주제 태그를 감점 신호로 | 작음 |

## 확인하지 못한 것
- 실제 DB 숫자(`keyword_signals` 건수, 표별 행 수, 사람별 추천 분포)는 서비스 키로 읽는 명령이 권한 확인에서 막혀 직접 세지 못했습니다. 위 숫자는 화면에 나온 값입니다.
- 임베딩 추천은 오늘 OpenRouter 무료 한도가 소진돼(429) 동작을 확인하지 못했습니다.
