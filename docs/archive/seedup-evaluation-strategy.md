# Seedup 평가와 해커톤 우승 전략

작성일 2026-11-16. 기준 코드는 `main`의 `fe33b53`입니다.

읽은 범위는 `AGENTS.md`, `README.md`, `docs/` 세 문서, 그리고 `lib/opportunities/`(엔진·수집기·검증 규칙·점수·스펙·LLM 호출), `lib/mcp/server.ts`, `components/Header.tsx`, 워크플로, 저장된 스냅샷 데이터입니다. 나머지 화면과 수집 라우트는 파일 목록과 크기만 봤습니다. 평가는 이 범위에서 내린 판단이고, 배포 사이트와 운영 DB는 보지 않았습니다.

## 1. 한 줄 결론

**기술은 탄탄하지만, 지금 데이터로는 핵심 주장인 "검증된 기회"를 뒷받침하지 못합니다.** 기능을 더 만들 때가 아니라, 데이터와 실제 사례로 주장을 증명할 때입니다.

## 2. 구조

### 2.1 전체 규모

- 커밋 84개, 2026-07-08부터 2026-11-14까지.
- 추적 파일 약 43,500줄. 그중 `package-lock.json`이 약 12,000줄입니다.
- 스택: Next.js 16, React 19, Supabase(pgvector), OpenRouter, Cloudflare Workers.

### 2.2 네 덩어리

| 덩어리 | 위치 | 하는 일 |
|---|---|---|
| 기회 엔진 | `lib/opportunities/` | 불만 수집, 원문 대조, 묶기, 경쟁 도구 조사, 점수 |
| 스펙과 전달 | `lib/opportunities/spec.ts`, `lib/mcp/`, `app/prd/` | 증언 → 요구사항 → 기능 → 화면 사슬, 에이전트 지침 내보내기, MCP 서버 |
| 내 씨앗 | `lib/seeds/`, `app/seeds/` | 내 GitHub 저장소 분석, 다음 기능 제안, 역기획 |
| 콘텐츠 | `lib/ingest/`, `app/news/`, `app/trends/` 등 | 뉴스·논문·트렌드·AI 제품 수집과 아티클 생성, 추천, 뉴스레터 |

눈에 띄는 점은 **코드의 무게가 핵심이 아닌 콘텐츠 쪽에 실려 있다**는 것입니다. `lib/ingest/ai.ts` 2,403줄, 아티클 생성 라우트 1,035줄, 트렌드 라우트 872줄, 추천 896줄입니다. 반면 서비스의 핵심인 기회 엔진은 `engine.ts` 320줄, `actors.ts` 291줄, `spec.ts` 317줄 정도입니다. 뉴스 큐레이션 서비스로 시작해 기회 엔진으로 방향을 바꾼 흔적으로 보이며, 메뉴에도 그대로 남아 있습니다(주 메뉴 4개, 더보기 5개).

### 2.3 기회 엔진이 실제로 하는 일

`lib/opportunities/engine.ts` 기준입니다.

1. 수집기 6개가 GitHub 이슈, Hacker News(Ask·댓글), Stack Overflow 미답변 질문, DEV.to, Lobsters에서 최근 365일 글을 모읍니다.
2. 불만 표현이 뚜렷한 글부터 최대 360건을 플랫폼별로 고르게 뽑습니다.
3. 모델이 8건씩 읽고 "새 도구로 풀 수 있는 불만"과 인용문을 뽑습니다.
4. `isVerbatimQuote`가 인용문이 원문에 실제로 있는지 확인합니다. 정규화한 뒤 15자 이상 부분 문자열로 들어 있어야 통과합니다.
5. 모델이 불만을 최대 16개 묶음으로 묶고, 묶음마다 이름·문제·검색어를 만듭니다.
6. 검색어로 같은 불만을 더 찾고(GitHub·HN·Stack Overflow), 이미 있는 도구를 찾습니다(GitHub 저장소·npm·Show HN·VS Code 마켓).
7. 모델이 도구를 직접 경쟁, 일부 겹침, 무관으로 분류하고 빈틈을 한 문장으로 씁니다.
8. 모든 인용을 최종 문제 정의에 대해 한 번 더 엄격하게 걸러냅니다.
9. 증언 3건 이상, 플랫폼 2종 이상이면 "기준 통과"로 표시합니다.

### 2.4 스펙이 실제로 보장하는 것

`normalizeSpec`(`lib/opportunities/spec.ts`)은 다음을 서버에서 강제합니다.

- 증언 번호를 하나도 인용하지 않은 요구사항은 가설(H)로 옮깁니다.
- 살아남은 요구사항에 연결되지 않은 기능, 살아남은 기능에 연결되지 않은 화면은 버립니다.

보장하지 않는 것도 분명히 알아야 합니다. **어떤 증언을 인용할지는 모델이 고르고, 서버는 그 번호가 존재하는지만 확인합니다.** 인용한 증언이 그 요구사항을 실제로 뒷받침하는지는 검사하지 않습니다. 발표에서 "모든 요구사항이 검증됐다"고 말하면 이 지점에서 반박당할 수 있습니다. 정확한 표현은 "모든 요구사항이 실제 원문을 가리키고, 가리키지 못한 것은 가설로 분리된다"입니다.

## 3. 데이터가 말하는 것

저장소에 들어 있는 스냅샷(`lib/opportunities/data/snapshot.json`, 2026-11-10 실행분) 기준입니다. 엔진이 매일 돌며 결과를 DB에 합치므로 운영 DB의 숫자는 이보다 많을 수 있습니다. 발표 전에 반드시 최신 숫자를 확인해야 합니다.

| 항목 | 값 |
|---|---|
| 수집한 글 | 399건 |
| 원문 대조를 통과한 불만 | 32건 |
| 대조에서 탈락한 인용 | 29건 |
| 기회 후보 | 28개 |
| **기준 통과 기회** | **2개** |
| 증언이 1건뿐인 후보 | 20개 |
| 증언이 2건인 후보 | 6개 |
| 증언 출처 | HN 27, Stack Overflow 9, GitHub 4 |
| DEV.to·Lobsters에서 나온 증언 | 0건 |
| 모델 호출 실패 | 158번 중 18번 |

기준을 통과한 두 기회는 "GIF 검색 API 대안"(증언 5건)과 "제공사별 모델 스키마 차이"(증언 3건)입니다.

여기서 나오는 판단은 세 가지입니다.

- **"검증된 기회 레이더"라고 부르기엔 검증된 기회가 2개입니다.** 후보의 70%는 글 하나에 기대고 있습니다. 심사위원이 직접 눌러 보면 바로 드러나는 가장 큰 약점입니다.
- **"5대 수요 플랫폼"은 실제로는 3개입니다.** DEV.to와 Lobsters는 수집만 되고 증언으로 살아남지 못했습니다.
- **탈락 29건은 오히려 강점입니다.** 최종 채택된 증언이 40건이니, 모델이 낸 인용 열 개 중 네 개꼴로 걸러냈다는 뜻입니다. "AI를 믿지 않는 구조"를 숫자로 보여줍니다. 탈락에는 원문 불일치와 관련성 재검사 탈락이 섞여 있으므로, 발표에 쓰려면 둘을 나눠 세어야 합니다.

## 4. 적중 기록 주장 점검

"28개 중 13개(46%)에서 불만이 먼저 나왔고 도구는 중간값 52일 뒤에 나왔다"는 숫자는 `lib/opportunities/insight.ts`의 `trackRecord`에서 나옵니다. 계산 방식은 "우리가 가진 가장 이른 증언보다 나중에 만들어진 관련 도구가 하나라도 있으면 적중"입니다.

이 숫자를 "선행 예측"의 증거로 쓰기에는 문제가 있습니다.

- **첫 증언이 세상의 첫 불만이 아닙니다.** 수집 범위가 최근 365일이라, 문제는 몇 년 전부터 있었을 수 있습니다.
- **비교 기준이 없습니다.** 개발 도구 분야에서는 어떤 주제를 골라도 1년 안에 관련 도구가 하나쯤 나옵니다. 무작위 주제의 적중률과 비교하지 않으면 46%가 높은지 알 수 없습니다.
- **"일부 겹침" 도구도 셉니다.** 직접 경쟁만 세면 숫자가 줄어듭니다.
- **표본이 28개이고, 그중 20개가 글 하나짜리입니다.**

권장은 둘 중 하나입니다. 표현을 "불만이 나온 뒤에 실제로 도구가 뒤따른 사례가 13건"으로 낮추거나, 무작위 주제 대비 비교 수치를 계산해 함께 보여주는 것입니다. 지금 표현 그대로 발표하면 통계를 아는 심사위원에게 반박당합니다.

## 5. 문서와 코드가 어긋난 곳

발표 자료와 README를 고칠 때 맞춰야 할 것들입니다.

| 항목 | 문서 | 실제 |
|---|---|---|
| 기회 점수 구성 | README: 수요 강도 40, 공급 빈틈 35, 최근성 25 | 코드: 증언 수 30, 플랫폼 폭 20, 반응 15, 최근성 15, 남은 빈틈 20 |
| 테스트 수 | README 66개, `next-tasks.md` 80개 | 이번에 실행하지 못함 (로컬에 `tsx`가 설치되어 있지 않음) |
| 수요 플랫폼 | 5대 플랫폼 | 증언이 나온 곳은 3개 |
| 원문 검증 | "100% 원문 글자 대조" | 15자 이상 부분 문자열 일치. 인용이 실재함은 보장하지만 관련성은 모델이 판단 |
| 모델 | 유료 모델로 전환 가능한 것처럼 읽힘 | `enforceFreeOnlyModels`가 무료 모델만 통과시킴. 전환하려면 `OPENROUTER_FREE_ONLY` 설정 확인 필요 |

## 6. 평가

### 강점

- **AI를 믿지 않는 구조.** 모델은 초안을 쓰고 서버가 판정합니다. 원문 대조, 가설 격리, 최종 관련성 재검사가 모두 코드로 강제됩니다. 이 설계가 Seedup에서 가장 참신한 부분입니다.
- **정직한 화면.** 기준 미달이면 "가설 초안" 표시를 붙이고, 화면 순서는 "모델이 제안한 것"이라고 밝힙니다. 한국 시장은 측정하지 못했다고 코드 주석과 화면에서 인정합니다.
- **끝까지 이어진 흐름.** 수집부터 코딩 에이전트 전달(MCP 도구 4개, 외부 의존성 없는 구현)까지 실제로 연결되어 있습니다.
- **운영 품질.** 일일 한도와 실패 시 환불, 캐시 대체, 수집 실패 격리, 매일 도는 엔진이 있습니다.

### 약점

- **필요성의 증거가 없습니다.** 써 본 사람, 이걸로 만들어진 결과물, 사용자 반응이 문서 어디에도 없습니다.
- **데이터가 얇습니다.** 3절 참고.
- **결과가 문서에서 끝납니다.** PRD가 아무리 정교해도 "그래서 뭐가 달라졌나"에 답하지 못합니다.
- **아이디어 유형이 참신하지 않습니다.** "도구를 만들기 위한 도구"이고, 나오는 기회도 전부 개발자 도구입니다.
- **범위가 넓습니다.** 메뉴 9개 중 핵심과 직접 관련된 것은 3개입니다.
- **쓰는 빈도가 낮습니다.** "뭘 만들지"는 프로젝트당 한 번 하는 고민입니다.
- **무료 모델 의존.** 엔진 한 번에 20분 넘게 걸리고 호출의 약 11%가 실패합니다.

### 개발자 한정은 코드에 박혀 있습니다

비개발자 문제로 넓히려면 세 곳을 바꿔야 합니다.

- `lib/opportunities/actors.ts`: 수집 소스 자체와 `DEV_TERMS` 필터.
- `lib/opportunities/engine.ts`의 추출 프롬프트: "software developers"를 위한 것만 남기고 소비자 주제는 버리라고 지시합니다.
- 같은 파일의 계획 프롬프트: "다른 소프트웨어 개발자가 쓰는 제품"만 적합하다고 판정합니다.

공급 조사도 GitHub·npm·VS Code 마켓이라 비개발자용 제품은 찾지 못합니다. 따라서 넓히는 일은 수집기 하나 추가로 끝나지 않는 중간 크기 작업입니다. 이전 대화에서 "소스 하나만 추가하면 된다"고 한 것은 코드를 읽기 전의 과소평가였습니다.

## 7. 기존 전략 문서에 대한 의견

`docs/final-report.md` 4절은 스펙과 코드 연결 검사, 지표 페이지, 인터뷰 루프, 알림, 다국어 수집원 같은 기능 추가를 우승 전략으로 제시합니다. 기능으로는 타당하지만, 데모데이에서 심사위원이 반복한 질문은 "정말 필요한가"였고 기능 추가는 그 질문에 답하지 못합니다. 같은 문서가 우선순위 1번으로 꼽은 "기준 통과 기회 10개 이상"과 6번 "데모 안정성"만 그대로 유지하고, 나머지는 사례 확보 뒤로 미루는 것을 권합니다.

## 8. 우승 전략

### 8.1 먼저 정할 것

해커톤 공지가 나오면 기존 프로젝트 출품이 가능한지 확인합니다.

- **출품 가능:** 아래 8.2부터 진행합니다.
- **불가능:** Seedup은 출품작이 아니라 준비 도구가 됩니다. `hackathon-topic-ideas.md`의 후보로 가고, Seedup에서 가져갈 것은 "모델이 쓴 문장을 원문과 대조해 못 믿으면 격리한다"는 설계입니다.

### 8.2 할 일 (중요한 순서)

**1. 사례 한 건 만들기**
- Seedup이 찾은 기회 하나로 작은 도구를 실제로 만듭니다. 기준을 통과한 "제공사별 모델 스키마 차이"가 후보입니다.
- 그 불만을 쓴 사람들의 글에 "이 문제를 풀어 봤다"고 답글을 달고 반응을 받습니다.
- 불만 원문, 스펙, 만든 도구, 작성자 반응을 발표의 뼈대로 씁니다.
- 반응이 없거나 부정적이어도 그 결과를 정직하게 보여주는 편이 사례가 없는 것보다 낫습니다.

**2. 기준 통과 기회 늘리기**
- 운영 DB의 현재 숫자를 먼저 확인합니다.
- 통과가 여전히 한 자릿수면 엔진을 반복 실행하고, 통과한 기회의 인용을 사람이 직접 읽어 검토합니다.
- 목표는 10개 이상입니다. 기준(3건, 2종)은 낮추지 않습니다.

**3. 한 줄기만 남기기**
- 메뉴에서 "오늘 읽을 것", "트렌드", "오픈소스", "AI 제품", "프로젝트", "아이디어 평가"를 숨깁니다(`components/Header.tsx`의 `PRIMARY`, `MORE`).
- 남기는 것은 기회, 스펙 작업 화면, 내 씨앗, 보관함입니다.

**4. 주장을 정확하게 고치기**
- 5절 표의 어긋난 곳을 README와 발표 자료에서 맞춥니다.
- 적중 기록은 4절의 권장대로 표현을 낮추거나 비교 수치를 추가합니다.

**5. 대상 사용자 좁히기**
- "개발자" 대신 "만들 수는 있는데 뭘 만들지 못 정한 1~2인 빌더"처럼 한 문장으로 씁니다.

**6. 데모 고정**
- 유료 모델 사용 여부를 정하고 설정을 확인합니다.
- 시연 동선의 결과를 미리 생성해 캐시에 넣고, 백업 영상을 녹화합니다.
- 배포 환경에서 스펙 생성, 슬롯, 수정, MCP, 공유 링크, 영어 모드를 실제로 돌려 봅니다. `next-tasks.md`에 아직 실제 DB와 모델로 검증하지 않았다고 적혀 있습니다.

**7. (선택) 현장 문제로 넓히기**
- 참신함 점수를 올릴 수 있는 가장 큰 변화지만 6절에 적은 대로 작업량이 작지 않습니다.
- 줄여서 하는 방법은 비개발자 불만 소스 하나를 수요 쪽에만 붙이고, 공급 상태는 이미 있는 `unknown`("기존 도구를 아직 조사하지 못함")으로 정직하게 표시하는 것입니다.
- 1번과 2번이 끝난 뒤에만 시작합니다.

### 8.3 발표에서 쓸 문장

- 한 문장 소개: "AI가 지어낸 기획서가 아니라, 실제 사람이 쓴 불만 원문을 가리키는 기획서를 코딩 에이전트에 넘깁니다."
- 가장 강한 장면: 요구사항을 누르면 실제 원문이 뜨고, 근거가 없는 항목이 가설로 떨어지는 순간.
- 가장 강한 숫자: 모델이 낸 인용 중 서버가 걸러낸 수(스냅샷 기준 채택 40건, 탈락 29건).

### 8.4 예상 질문과 답

| 질문 | 답 |
|---|---|
| 정말 필요한가 | 8.2의 1번 사례를 보여줍니다 |
| ChatGPT에 물으면 되지 않나 | ChatGPT는 근거를 지어내고, 그 문제를 겪는 실제 사람을 알려주지 못합니다 |
| 통과한 기회가 왜 이렇게 적은가 | 기준을 일부러 엄격하게 잡았고, 모델이 낸 인용 열 개 중 네 개꼴로 걸러냅니다. 숫자를 늘리려고 기준을 낮추지 않습니다 |
| 요구사항이 정말 그 증언에서 나온 건가 | 연결은 모델이 제안하고, 서버는 근거가 없는 항목을 분리합니다. 연결의 타당성은 사람이 원문을 눌러 확인할 수 있게 했습니다 |
| 적중 기록은 어떻게 계산했나 | 계산 방식과 한계를 그대로 설명합니다 (4절) |
| 글로벌에서 통하나 | 불만을 글로벌 플랫폼에서 모으고 번역해 주므로, 비영어권 빌더가 글로벌 시장의 문제를 읽을 수 있습니다 |
| 공개 글을 인용해도 되나 | 원문 링크를 함께 걸고, 자동으로 연락하지 않습니다 |
