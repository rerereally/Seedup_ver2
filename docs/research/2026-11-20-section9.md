# Seedup 계획 9절 조사

## 계획 9절을 이렇게 바꾸면 된다

아래는 **계획 세션에 전달할 제안**이다. 계획 원문과 코드는 수정하지 않았다.

1. **훅 형식 확인 항목을 줄인다.** Claude·Codex의 이벤트, JSON 입출력, matcher, Codex `/hooks` 신뢰 절차는 확인된 사실로 3-2에 옮긴다. B2에는 현재 묶음의 `/clear`·fork 누락, 경로 처리, JSON 파싱, upstream 없는 브랜치 처리를 남긴다. 3-8에는 Claude OTel 지표를 옮긴다. 새 확인 항목은 지원할 CLI 버전, 실제 압축·재개·중단 테스트, 로그 중복·마지막 기록 반영 지연이다. Codex 저장 로그의 내부 토큰 필드 검증은 남긴다.
2. **MCP 지원 여부를 클라이언트·표면별 표로 3-2에 옮긴다.** Claude Code·Codex·VS Code의 안내문 반영, Cursor·VS Code의 Apps 지원 등 확인분은 삭제한다. Cursor의 initialize instructions 반영과 Claude Code·Codex의 CLI 카드 렌더링은 별도 확인으로 남긴다. 고급 UI는 계속 선택 기능이며, 터미널 대화 승인 결정을 바꿀 근거는 아니다.
3. **GitHub 한도와 호출식을 3-4의 운영 제약으로 옮긴다.** 일반 PAT 기준 5,000회/시간, 보통 검증당 `5 + 파일 요청 수`회다. 남길 항목은 운영 토큰 종류·공유 사용량, 검증 p50/p95, 실패 파일 요청 상한, MCP·프록시 시간 제한이다.
4. **Workers 제한과 장기 실행 제품의 제공·가격은 3-4에 옮긴다.** HTTP 연결 중 경과 시간과 CPU 시간은 다르고, 응답 후 `waitUntil`은 최대 30초다. 새 확인 항목은 Seedup 실제 플랜·대시보드 CPU 설정·비동기 실행 기반 선택이다. 작업 ID 반환만으로 긴 작업의 생존이 보장되지는 않는다.
5. **Browser Rendering의 현재 이름 Browser Run, 플랜·가격·제한은 3-7에 옮긴다.** 실제 계정 제한과 시나리오당 브라우저 시간·종료 보장·캡처 보존 비용은 남긴다. 화면 평가 전체를 핵심 고리에 편입할 이유는 없다.
6. **외부 출처 확인을 ‘API 존재’와 ‘인용·보관 권한’으로 나눈다.** 3-10에 네이버 25,000회/일 및 저장 제한, YouTube 댓글 쿼터·30일 갱신/삭제를 사실로 옮긴다. 경쟁 앱 리뷰 RSS의 공식 지원·재이용 허락, 네이버의 Seedup 용도 승인, YouTube의 근거 분석·집계 방식 적합성은 남긴다. 세 출처를 영구 인용문 수집기로 확정하지 않는다.
7. **OpenRouter를 9절의 독립 항목으로 추가한다.** 두 모델의 정확한 ID와 `data_collection: "deny"` 의미는 1절 모델 결정·3-4에 옮긴다. 새 확인 항목은 모델별 정책 적합 endpoint, Safety Retention 허용 여부, 계정 자체 로깅 설정, 정책에 맞는 경로가 없을 때의 실패 처리다. 모델 목록 등재와 정책을 켠 요청의 성공을 구분한다.
8. **DB 필드 존재 여부는 확인 완료로 지운다.** 3-9에 ‘두 테이블 모두 라이선스·패키지 이름 전용 필드 없음’을 옮긴다. 새 확인 항목은 저장소↔패키지의 검증된 매핑·수집 시점·라이선스 미확인 후보 제외 방식이다. DB 후보 승격은 메타데이터 수집까지 포함하는 작업이다.

확인 기준일: **2026-11-20 (KST)**. 아래 모든 웹 링크의 확인 날짜도 이 날짜다. `확인`은 공식 문서 또는 저장소 정적 열람, `추정`은 명시한 가정에 따른 계산, `확인 못 함`은 문서·계정·실행 근거가 부족한 경우다. 제품 문서는 변경될 수 있으므로 설치 버전의 동작 보증과 구분한다. 금액은 USD, 세금·별도 서비스 비용 제외다.

조사 경계: 지정된 계획 절, 훅·GitHub 수집 코드·Wrangler 설정, 기여 규칙, 마이그레이션과 공식 공개 자료를 읽었다. `.env`, 실제 사용자 세션 로그, 계정 결제 화면은 읽지 않았다. 모델 추론·유료 API 호출은 하지 않았다. OpenRouter 공개 모델 메타데이터 GET만 확인했다. codebase-memory-mcp 출력과 운영 PRD 채움 비율은 제외했다.

## 1. 훅 형식과 사용량

### 1-1. Claude Code

**결론 — 세 이벤트 모두 stdin JSON이며, Stop의 `decision: "block"`과 `reason`으로 응답 종료를 막고 작업을 이어 가게 한다.** Stop은 세션 종료 자체가 아니라 응답 완료 시점이다.

**근거 (확인):** [Claude Code Hooks reference](https://code.claude.com/docs/en/hooks).

| 이벤트 | 입력 필드와 matcher |
| --- | --- |
| 공통 | `session_id`, `transcript_path`, `cwd`, `hook_event_name`. `permission_mode` 등은 이벤트·버전에 따라 추가되므로 항상 존재한다고 가정하지 않는다. |
| SessionStart | `source`: `startup`, `resume`, `clear`, `compact`, `fork`. matcher는 source의 정규식. `model`, `agent_type`, `session_title` 등은 선택 필드. |
| PreCompact | `trigger`: `manual` 또는 `auto`, `custom_instructions`: 수동 압축 지시 또는 `null`. matcher는 trigger. `source`를 기대하면 안 된다. |
| Stop | `stop_hook_active`, `last_assistant_message`, `background_tasks`, `session_crons`. matcher를 지원하지 않는다. `source`를 기대하면 안 된다. |

정상 종료 코드 0으로 stdout에 다음 JSON을 출력한다.

```json
{"decision":"block","reason":"검증되지 않은 작업의 인계 기록을 남기세요."}
```

또는 종료 코드 2와 stderr 사유로 계속하게 할 수 있다. `continue: false`는 에이전트 실행을 멈추는 의미라 대체물이 아니다. `stop_hook_active`를 확인해 반복을 피한다. SessionStart stdout 평문은 컨텍스트가 된다. Stop 시 transcript에 마지막 메시지가 아직 없을 수 있다는 공식 주의사항도 있다.

**계획 영향:** 3-2/B2는 시작·압축 뒤 재주입과 압축 직전 저장을 구분해야 한다. 3-4의 종료 경고는 강제 세션 종료·사용자 중단까지 보장하지 않는다. 3-8은 Stop 시점 한 번의 파일 읽기만으로 사용량 완전 수집을 보장할 수 없다. 핵심 고리의 훅 보완 규모이며 보류 기능을 확대할 사유는 아니다.

### 1-2. Claude OpenTelemetry

**결론 — 토큰은 `claude_code.token.usage`, 비용은 `claude_code.cost.usage`이며, 비용 지표는 청구서가 아닌 근삿값이다.**

**근거 (확인):** [Monitoring](https://code.claude.com/docs/en/monitoring-usage). 토큰 단위는 tokens, 비용 단위는 USD. 토큰의 `type`은 `input`, `output`, `cacheRead`, `cacheCreation`으로 나뉘며 `model`, `session.id` 등으로 구분한다. 일반 input은 캐시 읽기·쓰기 토큰을 포함하지 않는다. OTel은 별도 활성화와 exporter 설정이 필요하다.

**계획 영향:** 3-8/A1의 실측 수집 대안으로 명시할 수 있다. 캐시 구분 없이 전부 일반 input 단가로 계산하면 비용이 틀린다. 구독형 CLI의 모델 정가 환산 비용과 실제 결제액도 구분해야 한다. OTel 사용 시 수집·전송·중복 제거 범위가 추가되지만 새 평가 기능은 필요하지 않다.

### 1-3. Codex CLI 훅

**결론 — Codex도 수명주기 훅을 지원하며, 일반 사용자·프로젝트 훅은 `/hooks`에서 현재 정의를 검토하고 신뢰하기 전까지 실행하지 않는다.**

**근거 (확인):** [OpenAI 공식 Hooks 문서](https://learn.chatgpt.com/docs/hooks).

- 이벤트: `SessionStart`, `SessionEnd`, `PreToolUse`, `PermissionRequest`, `PostToolUse`, `PreCompact`, `PostCompact`, `UserPromptSubmit`, `SubagentStart`, `SubagentStop`, `Stop`, `Interrupt`, `PreModelRequest`, `PostModelRequest`.
- 명령 훅 입력은 stdin JSON. 공통 `session_id`, `transcript_path`(nullable), `cwd`, `hook_event_name`, `model`; 턴 이벤트에는 `turn_id` 등이 추가된다.
- SessionStart는 `source= startup|resume|clear|compact|fork`; 압축 이벤트는 `trigger=manual|auto`. Stop은 `stop_hook_active`, `last_assistant_message`를 받으며 matcher를 무시한다.
- 설정 위치는 사용자 `$CODEX_HOME/hooks.json`, 신뢰된 프로젝트 `.codex/hooks.json` 또는 `config.toml`의 `[hooks]`. 이벤트→matcher 그룹→handlers 구조다. command·MCP handler 지원, prompt·agent handler는 파싱하되 실행을 건너뛴다.
- Stop stdout JSON `{"decision":"block","reason":"..."}` 또는 exit 2 + stderr가 continuation을 만든다. 평문 stdout은 부적합하다. 관리형 훅은 정책 신뢰 예외이며, 일반 훅 변경은 재검토 대상이다.

**계획 영향:** 3-2/B2에서 ‘Codex 형식 미확인이라 AGENTS.md만’이라는 임시 전제를 해제할 수 있다. 단, 자동 실행은 사용자 신뢰 설정 이후다. Claude 설정 파일을 그대로 배포하는 것으로 끝나지 않는다. 지원 CLI 최소 버전과 Windows 경로·shell 검증은 새 확인 항목이다. 설치된 npm 패키지는 정적 열람상 `@openai/codex` 0.163.0이며, 이 버전에서 훅을 실행하거나 업데이트하지 않았다.

### 1-4. Codex 세션 로그와 토큰

**결론 — 저장 세션은 `rollout-*.jsonl`이지만 내부 transcript 스키마는 안정된 인터페이스가 아니다. 저장 로그의 정확한 토큰 JSON 경로는 이번 조사에서 확인 못 했다.**

**근거 (확인):** [NFS home 문서](https://learn.chatgpt.com/docs/environments/network-file-systems)는 기본 Codex home이 `~/.codex`이고 rollout JSONL에 대화 이벤트를 저장함을 설명한다. [Hooks 문서](https://learn.chatgpt.com/docs/hooks)는 `transcript_path` 형식이 변경될 수 있다고 명시한다. 사용자 로그는 열람하지 않았다.

**확인 못 함:** `~/.codex/sessions` 아래의 버전별 디렉터리 구조, 각 JSONL 행의 내부 envelope, `event_msg`/`token_count`, `info.total_token_usage`/`last_token_usage` 등의 정확한 경로와 누적 의미. 이 이름들을 구현 계약으로 확정하지 않는다.

대신 공개 문서에서 확인된 별도 인터페이스는 다음과 같다. **저장 세션 파일 형식과 혼동하면 안 된다.**

| 인터페이스 | 확인된 사용량 필드 |
| --- | --- |
| `codex exec --json` stdout JSONL | `type="turn.completed"`의 `usage.input_tokens`, `cached_input_tokens`, `output_tokens`, `reasoning_output_tokens` |
| `PostModelRequest` 훅 | `status`, `error`, `token_usage`(없으면 null). 각 모델 요청 시도·재시도를 관측함. 내부 token_usage 하위 필드는 해당 문서만으로 확정 못 함. |
| App Server | `thread/tokenUsage/updated` 알림 지원. 저장 rollout의 행 형식이라는 뜻은 아님. |

근거: [Non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode), [Hooks](https://learn.chatgpt.com/docs/hooks), [App Server](https://learn.chatgpt.com/docs/app-server).

**계획 영향:** 3-8/A1은 지원 버전을 고정한 비식별 fixture와 누적/증분·압축·재개·서브에이전트 중복 검증을 남겨야 한다. 누적 값을 매 행 더하는 구현은 피해야 한다는 설계상 판단이다. 문서화된 출력·훅 수집으로 바꾸는 선택은 계획 세션이 결정한다. 실측치 검증 전 절감액 표시는 보류하고 다른 보류 기능은 확대하지 않는다.

### 1-5. 현재 hook-bundle.ts 대조

**결론 — Claude JSON 설정과 Stop 반환은 맞지만, 목표 재주입의 일부 진입점과 계획의 압축 직전·정적 검사·사용량 수집은 구현되어 있지 않다.**

**근거 (코드 확인):** [hook-bundle.ts](../../lib/supervisor/hook-bundle.ts). 위 공식 훅 문서와 정적으로 대조했다. 실제 훅 실행 테스트는 하지 않았다.

**계획 영향:** 3-2/B2의 현재 훅 완료 범위를 ‘목표 스냅샷 주입 + 인계 권고’로 정확히 적는다. 3-4의 정적 검사와 3-8/A1 사용량 수집까지 완료됐다고 판단하면 안 된다. 형식 오류 수정과 아직 없는 기능을 구분해 작업량을 산정한다.

## 2. MCP 클라이언트별 지원

**결론 — instructions는 모델에 전달되는 안내이며 실행 강제가 아니다. Elicitation·Apps는 클라이언트와 실행 표면에 따라 다르므로 text fallback이 필요하다.**

**근거 (공식 문서 확인, 실기 미검증):** 각 셀의 링크 참조. `확인 못 함`은 미지원 판정이 아니다.

## 3. 검증 실행 환경

### 3-1. GitHub API 한도와 검증당 요청 수

**결론 — 일반 인증 사용자/PAT는 5,000회/시간이며, 현재 수집기는 보통 `5 + 파일 조회 시도 수`회의 REST 요청을 쓴다. 처리량은 실측이 아닌 예산 계산이다.**

**근거 (확인):** [GitHub REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api). PAT는 사용자 예산을 공유하므로 토큰 추가 발급으로 5,000회씩 늘지 않는다. GitHub App installation은 기본 5,000회 이상·조건별 증가, Enterprise 조건은 15,000회, Actions 내장 `GITHUB_TOKEN`은 보통 저장소당 1,000회/시간이다. 코드의 환경변수 이름 `GITHUB_TOKEN`만으로 토큰 종류는 알 수 없다. secondary limit도 별도다.

**코드 확인:** [lib/verifier/github.ts](../../lib/verifier/github.ts).

| 호출 | 코드 줄 | 횟수 |
| --- | --- | --- |
| 저장소 public 여부 | :59 | 1 |
| commit JSON / 바뀐 파일 목록 | :64–:70 | P = 1~30페이지 |
| 같은 commit의 diff | :73 | 1 (위 JSON 요청과 별개) |
| recursive tree | :74 | 1 |
| 각 파일 contents | :85–:99, 실제 요청 :92 | A = 조건을 통과해 요청한 파일 수, 실패 포함 |
| SHA의 check-runs | :104–:113 | C = 1~30페이지 (0개 결과여도 첫 요청 필요) |

**추정식:** 성공 경로 요청 수 `R = 3 + P + C + A`. commit 파일·check-runs 각각 1페이지면 `R = 5 + A`. 모든 파일 요청이 성공하고 총 용량 조건을 만족하면 A≤80이므로 보통 5~85회다. 30페이지 경계에서는 응답 수에 따라 incomplete 오류로 끝날 수 있다.

| 가정: P=C=1, 실패·재수집·다른 사용 없음 | 요청/검증 | 5,000회/시간 예산상 최대 검증 |
| --- | ---: | ---: |
| A=0 | 5 | 1,000 |
| A=5 | 10 | 500 |
| A=10 | 15 | 333 |
| A=20 | 25 | 200 |
| A=80 | 85 | 58 |

주의: :87은 `Object.keys(files).length`로 **성공한** 파일 80개를 제한한다. 요청 후 실패하거나 binary로 탈락하면 성공 수가 증가하지 않아 A는 80을 넘을 수 있다. 따라서 `143 = 3+30+30+80`을 코드 전체의 엄격한 최대 요청 수로 쓰면 틀린다. criterionPaths와 실패 시도에 별도 상한이 있는지는 이 파일만으로 보장되지 않는다. 재시도 기능은 get() 자체에는 없고, 검증 전체 재실행은 다시 예산을 쓴다.

**계획 영향:** 3-4 서버 검증의 요청 예산·대기열·캐시 재사용 조건으로 옮긴다. 하나의 서버 토큰이면 모든 사용자·프로젝트의 합계다. 정적 구조상 파일을 순차 조회하고 각 요청 timeout은 15초(:54)이므로 55초 내 종료를 보장하지 않는다. 실제 p50/p95와 토큰 종류·remaining/reset은 **확인 못 함**이다. push 자동 웹훅·GitHub App은 계속 보류해도 되지만 실패 요청 상한과 중복 수집 방지는 핵심 검증의 운영 보완이다.

### 3-2. Workers 실행 시간·CPU

**결론 — HTTP 연결이 살아 있는 동안 경과 시간의 고정 상한은 없지만, CPU와 응답 이후 작업 제한은 별도다. `waitUntil`은 긴 작업 큐를 대체하지 못한다. Seedup 요금제는 확인 못 함.**

**근거 (확인):** [Workers limits](https://developers.cloudflare.com/workers/platform/limits/), [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/).

| 항목 | Free | Paid / Standard |
| --- | --- | --- |
| HTTP 경과 시간 | 연결 유지 중 고정 상한 없음 | 동일 |
| 요청당 CPU | 10ms | 기본 30초, 설정으로 최대 300,000ms(5분) |
| 응답 완료/연결 종료 뒤 `waitUntil` | 최대 30초 | 최대 30초 |
| 외부 subrequests | 요청당 50 | 요청당 10,000 |
| 요청 비용 | 일 100,000회 포함 | 계정 월 최소 $5, 월 1,000만 회 포함, 초과 $0.30/100만 회 |
| CPU 비용 | 무료 한도 내 | 월 3,000만 CPU-ms 포함, 초과 $0.02/100만 CPU-ms |

네트워크 응답 대기는 CPU 시간에 포함되지 않는다. 프록시·MCP 클라이언트의 timeout이나 연결 종료는 별도 제약이다. Free에서는 GitHub 요청이 50회 넘는 경우 다른 외부 요청까지 합쳐 subrequest 제한에 먼저 걸릴 수 있다.

**코드 확인:** [wrangler.jsonc](../../wrangler.jsonc):3–:6은 Worker·compatibility 설정, :20–:26은 자체 rate limit binding이다. :1–:35 전체에 `limits.cpu_ms`, Workflows·Durable Objects·Queues·Browser binding은 없다. 이 파일로 결제 플랜이나 대시보드 설정은 알 수 없다. `compatibility_date`나 자체 rate limit을 Paid 증거로 쓰지 않는다.

**계획 영향:** 3-4의 ‘작업 ID 반환→get_verification’은 영속 작업 실행 기반까지 명시해야 한다. 응답 후 30초 넘는 처리를 메모리 작업으로만 남기는 설계는 보완이 필요하다. 경과 시간·CPU·subrequest를 함께 측정하고, 장기 실행 도입 여부는 계획 세션이 결정한다. 사용자 저장소 CI로 판정 위치를 옮길 이유는 없다.

### 3-3. Workflows·Durable Objects·Queues 플랜과 가격

**결론 — 현재 세 제품 모두 Workers Free·Paid에서 제공된다. 무료 제공 여부만으로 장기 검증에 충분하다고 판단하면 안 된다.**

**근거 (확인):** 제품별 공식 가격표. Paid는 Workers 계정 기본료와 각 제품 초과 사용료를 함께 고려한다.

| 제품·근거 | Free 포함량 | Paid 포함량·초과 가격 |

| [Workflows](https://developers.cloudflare.com/workflows/reference/pricing/) | 요청 일 100,000회(Workers와 공유), 호출당 CPU 10ms, 저장 1GB-month, step 일 3,000회 | 요청 월 1,000만 회 + $0.30/100만, CPU 월 3,000만ms + $0.02/100만ms, 저장 1GB-month + $0.20/GB-month, step 월 500,000회 + $0.80/100,000회 |

Workflows의 step·storage 과금은 2026-08-10부터 적용된 현재 가격이다. DO duration은 활성 메모리의 경과 시간 과금이고, 네트워크 대기가 CPU가 아니라는 Workers 설명과 혼동하면 안 된다. 새 DO는 SQLite가 기본 선택이며 KV backend는 기존 namespace 계정 조건이 있다. Queues는 64KB 단위·메시지별 연산이며 보통 전달 1건에 write/read/delete 3 operations, 재시도는 추가 사용량이다.

**계획 영향:** 3-4의 긴 검증은 Workflows의 단계 저장·재시도, Queues의 분리 실행, DO의 상태·조정 역할을 비교하는 구현 선택이 된다. ‘job id 문자열만 반환’보다 작업 크기가 커지므로 실제 지연 검증 뒤 최소 기반을 고른다. 제공 플랜 조사는 완료할 수 있지만 Seedup 계정 적용 가능량·예상 월 비용은 **확인 못 함**이다. 보류된 전체 자동화 범위를 당겨올 근거는 아니다.

## 5. 외부 근거 출처의 약관·API

### 5-1. App Store 고객 리뷰

**결론 — 자기 앱 리뷰의 공식 API는 확인했지만, 경쟁 앱 리뷰 RSS의 현재 공식 지원 계약과 원문 일부를 영구 저장·재게시할 권한은 확인 못 했다.**

**근거 (확인):** Apple [Customer Reviews 공식 문서](https://developer.apple.com/documentation/appstoreconnectapi/customer-reviews.md)는 **your app** 리뷰 조회를 설명한다. 앱·버전별 조회, territory·rating 필터가 있다. [RSS Builder](https://rss.marketingtools.apple.com/)는 공식 피드 생성 서비스지만 경쟁 앱 고객 리뷰 피드를 현재 지원하는 근거는 얻지 못했다. [App Review Guidelines 4.5.1](https://developer.apple.com/app-store/review/guidelines/#apple-sites-and-services)은 승인된 Apple RSS 사용과 Apple 사이트 scraping을 구분한다. 이 가이드만으로 Seedup 웹 서비스에 인용 재배포 허락이 생기지는 않는다.

`itunes.apple.com/{country}/rss/customerreviews/...`라는 과거 경로는 알려져 있으나, 이번 공개 GET은 도구에서 접근 실패해 현재 응답도 검증하지 못했다. 도메인이 Apple이라는 사실, 공개 접근 가능성, 공식 지원·저작권 재이용 허락은 각각 별개다. 10페이지·500개 같은 수치도 현재 공식 보장으로 채택하지 않는다.

**계획 영향:** 3-10의 경쟁 앱 1~3점 리뷰 수집은 보류 유지. API 연동만의 작은 작업으로 잡지 말고 접근·재이용 근거 확인을 선행한다. 자기 앱 리뷰 반입도 고객 리뷰의 권리까지 자동 이전된다는 뜻은 아니다. 승인된 제공 경로·인용 범위·삭제 정책이 확인되기 전에는 영구 R-n 근거 수집으로 확정하지 않는다.

### 5-2. 네이버 블로그·카페·지식iN

**결론 — 세 검색 API는 존재하고 하루 합산 25,000회지만, 검색결과를 장기 저장·재가공하는 근거 DB 용도는 공식 FAQ가 허용하지 않는다. Seedup의 상업 이용 가능 여부는 별도 확인이 필요하다.**

**근거 (확인):** [블로그 검색](https://developers.naver.com/docs/serviceapi/search/blog/blog.md), [카페글 검색](https://developers.naver.com/docs/serviceapi/search/cafearticle/cafearticle.md), [지식iN 검색](https://developers.naver.com/docs/serviceapi/search/kin/kin.md). JSON endpoint는 `/v1/search/blog.json`, `cafearticle.json`, `kin.json`. API 사용량은 client ID별 합산이고 카페는 공개 게시판 검색이다. 반환 `description`은 검색 요약으로 원문 전체 API가 아니다.

[NAVER Developers FAQ](https://developers.naver.com/products/intro/faq/faq.md)는 부하 방지용 단순 캐시 외 별도 저장·재가공을 허용하지 않는다고 안내한다. 상업 목적 검색결과 이용 제한과 광고·스폰서·유료 회원 접근 사례도 제시한다. 이 FAQ에는 오래된 API 설명도 섞여 있어, 현재 계약·Seedup의 분석/인용 용도에 대한 예외 승인은 **확인 못 함**이다. ‘API 무료’나 ‘Seedup 무료 베타’만으로 영구 저장이 허용된다고 해석하지 않는다.

**계획 영향:** 3-10의 한국어 출처 수집은 검색 결과 탐색과 원문 인용문 보관을 분리해야 한다. 검색 API 권한으로 게시글 저작권자의 인용·재배포 권한까지 얻는 것은 아니다. 현 계획의 글자 대조·장기 근거 보관을 그대로 적용하려면 제공자 허락과 원문별 권리 검토가 남는다. 크롤링으로 우회하는 것을 대안으로 확정하지 않는다. 보류 기능은 정책 확인까지 포함하는 규모다.

### 5-3. YouTube 댓글

**결론 — 댓글 조회는 저렴한 쿼터로 가능하지만, API로 가져온 댓글 일부도 무기한 고정 근거로 보관할 수 있다고 볼 수 없다. 기본적으로 30일 내 갱신 또는 삭제가 필요하다.**

**근거 (확인):** [commentThreads.list](https://developers.google.com/youtube/data/reference/rest/v3/commentThreads/list)는 요청당 1 unit, maxResults 100, `videoId` 필터를 지원한다. 댓글 thread 응답의 replies가 전체 대댓글을 보장하지 않으므로 추가 댓글 조회가 필요할 수 있다. [Data API overview](https://developers.google.com/youtube/data/getting-started)의 현재 기본 배정은 기타 endpoint 합산 일 10,000 units이며 search.list·videos.insert는 별도 기본 호출 배정을 설명한다. 댓글 조회만·1페이지/건이면 일 약 10,000요청이라는 계산이고 댓글 수 보장은 아니다.

[Developer Policies III.E.4](https://developers.google.com/youtube/terms/developer-policies/)는 일반 Authorized Data와 제한된 Non-Authorized Data의 임시 보관을 규정하고 30일 뒤 갱신·삭제, 최신 데이터 반영을 요구한다. 공개 댓글의 발췌도 API Data 일부라는 이유로 보관 규칙을 무시할 수 없다. 같은 정책의 집계·파생 지표·사용 목적 제한도 검토해야 하므로 ‘30일 갱신하면 모든 제품 분석이 허용’이라고 결론 내리지 않는다. 독립적인 저작권 인용 허용성까지 확정한 것은 아니다.

**계획 영향:** 3-10에서 댓글 ID·출처 URL·조회일·재확인 기한, 수정/삭제 전파, 인용문 철회 상태가 필요하다. 원문이 없어졌을 때 영구 보존한 인용을 계속 ‘현재 공개 원문 검증’으로 표시하면 안 된다. Seedup의 댓글 분석·외부 모델 전송·집계 용도가 허용되는지는 **확인 못 함**으로 남긴다. 단순 검색 커넥터보다 유지 작업이 커지며 트랙 B 보류 유지가 적절하다.

## 6. OpenRouter 모델과 데이터 수집 거부

### 6-1. data_collection의 실제 의미

**결론 — `provider.data_collection: "deny"`는 수집 정책에 맞지 않는 provider endpoint를 라우팅 후보에서 제외하는 옵션이다. 모든 저장 금지나 OpenRouter 자체 로깅 해제를 뜻하지 않는다.**

**근거 (확인):** [Provider Routing / Data policies](https://openrouter.ai/docs/guides/routing/provider-selection#requiring-providers-to-comply-with-data-policies)는 기본값 allow, deny는 데이터를 수집하지 않는 provider만 사용한다고 설명한다. 정책 표시는 OpenRouter가 아는 범위의 provider 정책 정보라는 한계도 명시한다. [Provider Logging](https://openrouter.ai/docs/guides/privacy/provider-logging)은 학습 제외와 보관을 구분하고 자체 OpenRouter 설정은 별개라고 한다.

[ZDR 문서](https://openrouter.ai/docs/guides/features/zdr)는 ZDR, Safety Retention(안전 목적 보관·학습 없음), Retention and Training을 구분한다. 현재 `zdr:true`도 계정·guardrail의 Safety Retention 허용 선택을 따른다. 엄격한 무보관이면 계정에서 ZDR only 선택 여부까지 확인해야 한다. [Data Collection](https://openrouter.ai/docs/guides/privacy/data-collection)은 자체 입출력 로깅·제품 개선 동의, 메타데이터 보관, 법적 보존 예외를 별도로 설명한다.

**계획 영향:** 1절·3-4와 단계 2 B1의 ‘데이터 수집 거부 유료 경로’를 ‘학습/수집 거부’, ‘안전 목적 보관 허용 여부’, ‘자체 로깅’으로 구체화한다. deny를 붙였다는 이유만으로 사용자에게 ‘어디에도 저장되지 않음’을 약속하면 안 된다. 정책 불충족 시 일반 provider로 몰래 완화하지 않고 실패·재시도 처리하는 작은 운영 계약이 필요하다.

### 6-2. 두 모델의 ID와 정책 적합 경로

**결론 — 두 모델은 OpenRouter 카탈로그·공개 endpoint 목록에 있다. deny 옵션과 함께 요청하는 구성은 가능하지만, 현재 계정의 정책 적합 경로에서 추론 요청이 성공하는지는 확인 못 했다.**

| 계획 모델 | 확인된 모델 ID | 확인 범위 |
| --- | --- | --- |
| GPT 6.2 Sol | `openai/gpt-6.2-sol` | [모델 페이지](https://openrouter.ai/openai/gpt-6.2-sol), [공개 endpoints](https://openrouter.ai/api/v1/models/openai/gpt-6.2-sol/endpoints)에 등재. OpenAI·Azure·Amazon Bedrock 경로 확인. |
| Haiku 5.5 | `anthropic/claude-haiku-5.5` | [모델 페이지](https://openrouter.ai/anthropic/claude-haiku-5.5), [공개 endpoints](https://openrouter.ai/api/v1/models/anthropic/claude-haiku-5.5/endpoints)에 등재. |

**확인:** provider 필터는 모델 ID와 함께 보내는 공통 라우팅 옵션이다. **확인 못 함:** 공개 목록만으로 모든 endpoint의 현재 data policy를 확정하지 못했고, 유료 추론·계정 설정 조회를 하지 않았다. 따라서 ‘두 모델이 deny 아래 항상 호출 가능’ 또는 ‘전 경로 ZDR’이라고 쓰지 않는다. 조건에 맞는 provider가 없으면 오류가 날 수 있다. [공식 Support](https://openrouter.ai/support)는 privacy 조건을 만족하는 provider가 없을 때 error가 난다고 설명한다.

**계획 영향:** 1절의 모델 이름을 다른 모델로 교체할 근거는 없다. 3-4/B1에는 정확한 ID와 필터 실패 시 UI·사용량 환불 처리를 반영할 수 있다. 실제 운영 키로의 정책 경로 확인은 승인된 후속 운영 검증으로 남긴다. 모델 2개 확인을 이유로 화면 평가·전체 자동화를 추가하지 않는다.

## 7. DB의 라이선스·패키지 필드

**결론 — 마이그레이션 기준 `github_trends`, `ai_products` 모두 라이선스·정확한 패키지 이름을 저장할 전용 필드가 없다. 운영 DB의 실제 상태는 확인 못 함.**

**근거 (코드 확인):** `supabase/migrations` 전체를 `license|package|npm` 및 두 테이블 생성·변경문으로 검색하고 관련 DDL을 열람했다.

| 테이블 | 기존 관련 필드 | 없는 필드·주의 |
| --- | --- | --- |
| `github_trends` | [initial.sql:415](../../supabase/migrations/20261101000000_initial.sql#L415)의 `repo_full_name`, `repo_url`, stars, forks, language, topics, pushed_at. `latest_release`는 [repo_releases.sql:3](../../supabase/migrations/20261118120720_repo_releases.sql#L3)에서 추가 | license/SPDX, package name, registry, package version·검증 출처 없음. release JSON은 라이선스·패키지 관계의 계약이 아니다. |
| `ai_products` | [initial.sql:242](../../supabase/migrations/20261101000000_initial.sql#L242)의 name, website_url, source, product_hunt_url, pricing_type 등 | 제품 name은 npm package name이 아니다. 라이선스, 검증된 GitHub 저장소·패키지 매핑 전용 필드 없음. |

**외부에서 얻는 방법 (공식 근거 확인):** [GitHub licenses API](https://docs.github.com/en/rest/licenses/licenses)는 저장소 정보의 license와 `GET /repos/{owner}/{repo}/license`를 제공한다. `license.spdx_id`·key·name 및 실제 LICENSE를 확인할 수 있다. 자동 탐지는 알려진 LICENSE 텍스트 기준이며 의존성 전체의 라이선스까지 보장하지 않는다. null·NOASSERTION을 ‘자유 사용 가능’으로 승격하면 안 된다.

[npm package.json 문서](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/)의 `name`, `version`, `license`, `repository`와 실제 레지스트리 메타데이터를 대조해 패키지 이름을 확인한다. monorepo는 하위 패키지가 여럿이고 저장소 이름과 package name이 다를 수 있다. PyPI 등 다른 registry도 해당 배포 메타데이터·저장소 연결을 검증하는 방식이 필요하다. 폐쇄형 AI 제품은 npm 패키지·오픈소스 라이선스가 아예 적용되지 않을 수 있다.

**계획 영향:** 3-9의 DB 후보 승격은 현재 필드만으로 라이선스·패키지 기준을 충족할 수 없다. 제안 데이터는 registry, 정확한 package name/version, repo·manifest 경로·SHA, SPDX/라이선스 원문 URL, 확인 시각·상태다. 이는 **새 스키마 제안**이며 어떤 마이그레이션도 추가하지 않았다. 검증된 고정 목록을 먼저 쓰는 핵심 범위는 유지하고, DB 자동 승격은 수집·매핑 검증까지 포함한 보류 작업으로 산정한다.

## 남은 확인 항목의 완료 조건

- **훅/사용량:** 지원 CLI 버전별 비식별 fixture로 시작·clear·fork·압축·중단·재개, 캐시·서브에이전트·누적 토큰 중복을 재현한다. 저장 로그의 토큰 경로를 아직 확정하지 않았다.

- **검증 운영:** Seedup 실제 플랜/CPU 설정·GitHub 토큰 종류와 공유량, 코드+모델 전체 p50/p95·연결 종료 후 작업 생존을 확인한다.

- **DB:** 운영 스키마 대조와 라이선스·registry 매핑 설계를 후속 칸으로 결정한다. 이번에는 마이그레이션 정의만 확인했다.
