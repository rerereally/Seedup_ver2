## 장면 1. 문제 정의와 한 줄 정의 (0:00–1:30)

- **대응 기준:** `01 문제 정의 및 프로젝트 임팩트 (20점)` — 문제 명확성 · 실제 해결 기여 · 적용 가능성과 기대효과
- **화면 경로:** 발표 슬라이드 (표지 · 문제 정의 · 한 줄 정의) → `/` (홈 첫 화면)
- **상태 구분:** 문제 정의와 서비스 방향(`docs/supervisor-plan.md` 0절)

> 안녕하세요. AI 네이티브 1인 빌더를 위한 서비스 **Seedup**을 발표하겠습니다.
>
> 먼저 우리가 풀려는 문제입니다. Claude Code나 Codex 같은 코딩 에이전트 덕분에 코드를 쓰는 속도는 크게 빨라졌습니다. 그런데 혼자 에이전트로 제품을 만들다 보면, 코드보다 먼저 무너지는 것이 있습니다. **처음 정한 목표와 근거**입니다.
>
> 실제 개발 현장에서 세 가지 문제가 반복됩니다.
> 첫째, 시작할 때부터 "무엇을 왜 만드는지"에 근거가 약합니다. 일반 LLM에게 아이디어를 물으면 대부분 좋다고 맞장구치거나 없는 근거를 지어냅니다.
> 둘째, 구현에 들어가도 대화가 길어지거나 세션이 압축되면 처음 정한 목표가 흐려집니다. 도구를 바꾸면 맥락은 도구마다 끊깁니다.
> 셋째, 완료 판정을 코드를 쓴 모델이 같은 세션에서 스스로 보고합니다. 명세에 없는 기능이나 범위 밖 변경이 섞여도 그대로 지나갑니다.
>
> **Seedup은 처음 정한 목표를 중심축으로 고정하고, 기획부터 개발과 평가까지 흐름이 그 목표를 향하도록 잡아 주는 서비스입니다.**
>
> 적용 대상은 **Claude Code와 Codex를 쓰는 AI 네이티브 1인 빌더**입니다. 코드는 기존 코딩 에이전트가 씁니다. Seedup은 그 바깥에서 세 가지를 쥡니다.
> **무엇을 왜 만드나**(목표 · 근거 · 명세), **어디까지 왔나**(진행 상태 · 다음 작업 · 사람 할 일), 그리고 **정말 그렇게 됐나**(실제 코드 · CI · 화면으로 판정)입니다.
>
> 우리의 북극성 지표는 **목표 도달률**, 즉 완료 시점에 충족된 성공 기준의 비율입니다. "한 줄로 배포까지 자동 생성"이 아니라, 처음 정한 목표에 실제로 도달하게 만드는 것이 Seedup의 기대효과입니다.

## 장면 2. 독창성과 차별점 (1:30–2:40)

- **대응 기준:** `02 아이디어의 독창성 및 혁신성 (20점)` — 기존과 차별화된 독창성 · AI 활용의 새로운 가치 · 단순 구현을 넘은 관점
- **화면 경로:** 발표 슬라이드 (`Claude Code · Codex vs Seedup` 비교표 + `모델을 믿지 않는 네 겹의 확인`)
- **상태 구분:** 지금 구현된 근거 검증 구조와 단계 1~2로 확장할 감독관 구조를 구분해 설명

> "그냥 Claude Code나 ChatGPT에 PRD를 써 달라고 하면 되지 않나요?" 심사위원분들이 가장 먼저 떠올리실 질문입니다. Seedup의 관점은 두 가지에서 다릅니다.
>
> **첫째, 에이전트를 대체하지 않고 에이전트 '바깥'의 중심축을 쥡니다.**
> Claude Code나 Codex 안에서는 목표가 대화와 로컬 메모리 파일에 있어 세션이 끝나거나 압축되면 흐려지고, 기억도 도구마다 따로 놉니다. Seedup은 도구와 무관한 서버 쪽에 원문 근거와 명세, 작업 상태를 둡니다. 지금도 PRD 고정과 진행 상태 · 커밋 연결이 서버에 남고, 앞으로 단계 1과 단계 2에서 서버에 잠긴 목표와 다른 계열 모델 기반 교차 판정, 범위 이탈 경고를 붙일 계획입니다.
>
> **둘째, AI를 활용하되 '모델을 믿지 않는 구조'로 설계했습니다.**
> 기존 AI PRD 도구는 모델이 한 번에 그럴듯한 문서를 쓰면 끝납니다. Seedup은 무료 LLM이 틀리거나 지어내는 것을 전제로, **초안은 모델이 쓰고 채택과 검증은 코드와 다른 모델이 맡도록** 역할을 분리했습니다. 이 네 겹의 확인 구조가 지금 실제로 어떻게 돌아가는지 라이브 화면으로 바로 보여 드리겠습니다.

## 장면 3. 지금 되는 것 — 대표 흐름 라이브 시연 (2:40–5:20)

- **대응 기준:** `01 문제 정의 및 임팩트` + `04 실용성` (실제 배포 환경 동작 확인)
- **화면 경로:** `/` → `/newsletter-preview` → `/opportunities/[slug]` → `/prd/new` → `/prd/validate` → `/spec/[id]` → `/agents`
- **상태 구분:** 이 장면에서 보여 주는 기능은 **모두 지금 운영 코드에서 실제로 동작하는 기능**입니다.

> 지금 바로 운영 사이트에서 동작하는 대표 흐름, **아이디어 → 원문 → PRD → `AGENTS.md` / MCP** 순서대로 보여 드리겠습니다.
>
> **[화면: `/` → `/newsletter-preview` → `/opportunities/[slug]`]**
> 먼저 홈 화면(`/`)입니다. 아이디어를 한 줄 입력하면 `/prd/new`로 이어지면서, GitHub 이슈 · Hacker News · Stack Overflow 등 공개 개발자 글에서 수집해 둔 실제 불만 원문 중 가까운 글을 바로 찾아 줍니다. 반대로 "뭘 만들지"부터 찾고 싶다면 `/newsletter-preview`에서 검증 기준을 통과한 문제 목록을 보고, `/opportunities/[slug]`에서 영어 원문 · 한국어 번역 · 원문 링크와 이미 존재하는 경쟁 도구를 확인할 수 있습니다. 이때 모델이 뽑은 인용은 **원문에 글자 그대로 있을 때만** 채택됩니다.
>
> **[화면: `/prd/new` (질문 → PRD 스트리밍 → 근거 추적 · 5가지 보기) → `/prd/validate` → `/spec/[id]`]**
> 다음은 `/prd/new`입니다. 아이디어와 가까운 원문을 바탕으로 PRD를 바꾸는 핵심 결정만 짧은 객관식 질문으로 먼저 묻습니다. 답을 고르면 PRD가 쓰는 대로 화면에 스트리밍되고, 생성이 끝나면 서버가 문서를 구조로 읽어 **증언(`E`) → 요구사항(`R`) → 기능(`F`) → 화면(`S`)** 추적 연결을 강제합니다.
> 여기서 중요한 점은, 원문 근거가 없는 요구사항은 서버가 자동으로 **가설(`H-n`)**로 분리한다는 것입니다. 항목을 누르면 어떤 실제 원문에서 나왔는지 추적 선이 바로 강조되고, 기능마다 입력 · 예외 · 권한 · 완료 기준 같은 개발 준비 슬롯이 붙어 정해지지 않은 것은 에이전트가 먼저 묻도록 표시됩니다. 완성된 PRD는 `/spec/[id]` 읽기 전용 링크로 공유할 수 있고, 만들기 전에 실패 이유부터 따져 보는 검증 리포트도 `/prd/validate`에서 지금 동작합니다.
>
> **[화면: `/prd/new` 내보내기 → `/agents`]**
> 마지막으로 기획에서 코딩으로 끊기지 않고 넘어가는 단계입니다. `/prd/new`에서 이 PRD를 `AGENTS.md`, `CLAUDE.md`, `.cursor/rules` 파일로 바로 내보낼 수 있습니다. 그리고 `/agents` 화면에서 자신이 쓰는 도구(Claude Code, Codex, Cursor 등)를 고르면 개인 토큰 발급과 MCP 연결 설정이 한 번에 준비됩니다. 지금도 에이전트가 Seedup MCP 서버에 연결해 `get_next_task`로 다음 기능과 원문을 받아 구현하고, `update_feature_status`와 `link_commit`으로 진행 상태와 커밋을 기록하며, 완료된 기능의 파일을 건드리면 자동으로 재확인(`needs_recheck`) 표시가 걸립니다.

## 장면 4. AI 기술 이해도 · 원리 · 실측 성적표 · 한계 (5:20–7:30)

- **대응 기준:** `03 AI 기술 이해도 및 활용 적절성 (20점)` — 기술과 원리 이해 · 적합한 기술 선택 · 개선 가능성과 한계 고려
- **화면 경로:** 발표 슬라이드 (AI 파이프라인 · 무료 모델 대응 · `docs/scorecard.md` 성적표 · 목표 채움 기준선)
- **상태 구분:** 아래 기술과 숫자는 모두 **현재 구현 및 실측값**(`docs/scorecard.md`, `eval-results/2026-11-20-goal-baseline.json`)입니다.

> 이제 이 흐름을 지탱하는 AI 기술 선택과 실측 결과, 그리고 한계를 말씀드리겠습니다.
>
> **첫째, 문제에 맞춘 기술 선택과 원리입니다.**
> - **환각 방지:** 인용 채택은 LLM이 아니라 코드의 글자 대조(`isVerbatimQuote`)가 결정합니다. 요구사항 · 기능 · 화면의 참조 무결성도 `normalizeSpec` 코드가 강제해 근거 없는 요구사항은 `H-n` 가설로 내립니다.
> - **임베딩 2-Pass 군집:** 비슷한 불만을 한 문제로 묶을 때 한 번 군집화한 뒤 모든 글을 최종 중심과 다시 비교(`clusterByEmbedding`)해, 입력 순서 때문에 동떨어진 글이 줄줄이 붙는 체이닝 오류를 막았습니다.
> - **교차 모델 P0 감사:** PRD 초안이 나오면 작성 모델과 **다른 모델(P0 Critic)**이 핵심 요구사항(P0)마다 인용 원문이 정말 뒷받침하는지 다시 검토합니다. 자기 출력에 관대한 모델 편향을 줄이기 위한 선택입니다.
> - **무료 모델 한계 대응:** 운영 비용을 낮추기 위해 무료 OpenRouter 모델을 쓰면서 생긴 문제들을 공학적으로 대응했습니다. 생각 토큰 때문에 답이 비는 문제는 출력 한도 **16k**로, 응답이 멈추는 문제는 **첫 토큰 15초 · 무응답 25초** 감시 후 대체 모델 자동 전환으로, 생성 실패는 **사용량 환불**과 **동일 근거 캐시**로 처리했습니다.
>
> **둘째, 감이 아니라 고정 평가셋으로 잰 실측 성적표입니다.** (`docs/scorecard.md`, 2026-11-19 기준)
> - 고정 20건 PRD 품질 평가에서 생성 성공은 **19/20에서 20/20**으로, PRD당 형식 지적은 **0.7에서 0**으로 줄었습니다.
> - 내용 종합 점수는 10점 만점에 **3.0에서 7.4**로 올랐습니다. 세부 항목은 구체성 **1.9 → 4.0**, 근거 **1.9 → 2.8**, 읽기 **3.2 → 4.65**, 실행 가능성 **1.6 → 4.2**, 완결성 **2.3 → 4.85**입니다. 생성 시간 중간값도 **64초에서 55초**로 줄었습니다.
> - 운영 공개 인용 정밀도는 **83% (52/63)**이며, 검증 리포트는 **200초 이상에서 49~94초**로 단축됐습니다.
> - 매일 수집 8단계는 Worker 시간 제한 실패에서 **모두 성공(아티클 생성 포함 28분)**으로 안정화했고, 운영 smoke는 **14/14**, 질문 → PRD → 수정 → MCP 흐름 점검은 **4/4** 통과했습니다.
>
> **셋째, 오늘 직접 잰 기준선과 솔직한 한계입니다.**

## 부록 1. 5분 질의응답(Q&A) 핵심 대비

### Q1. 오늘 잰 운영 PRD 저장 건수가 0건인데, 실제로 쓸 수 있는 서비스가 맞나요?
- 맞습니다. 발표에서 보여 드린 대표 흐름(아이디어 → 원문 → PRD → 내보내기 → MCP)은 지금 운영 사이트에서 동작하며, 흐름 점검 `4/4`와 운영 smoke `14/14`를 통과했습니다.
- 다만 아직 외부 베타 홍보 전이고 팀 내부 테스트 위주였으며, 저장 버튼 흐름을 점검하는 과제(`3-5 저장 0건 원인`)가 단계 0에 남아 있어 `evidence_dossiers`에 저장된 행이 0건이었습니다. 숫자를 부풀리지 않고 0건을 기준선으로 기록한 뒤, 단계 0 베타 공개와 단계 1 목표 잠금 이후 같은 스크립트(`scripts/eval-goal.ts`)로 변화를 추적할 계획입니다.

### Q2. PRD 내용 점수 `7.4/10`을 무료 모델 하나로 채점했다면 신뢰할 수 있나요?
- 그 한계를 인지하고 있어 `docs/scorecard.md`와 발표에서 채점 모델(`nvidia/nemotron-3-ultra-550b-a55b:free`)을 명시했습니다.
- 같은 고정 20건과 같은 채점 모델로 **개선 전(3.0)과 후(7.4)의 상대 변화**를 확인한 데 의미가 있고, 생성 성공(`19/20 → 20/20`)과 형식 지적(`0.7 → 0`)은 모델이 아니라 코드로 집계했습니다. 다음 단계에서는 다른 계열 모델과 사람 블라인드 채점으로 보강할 계획입니다.

### Q3. 인용 정밀도가 `83% (52/63)`인데, 글자 대조를 하는데도 왜 100%가 아닌가요?
- `isVerbatimQuote`는 "모델이 뽑은 문장이 실제 원문에 글자 그대로 존재하는가"를 100% 보장하지만, "그 문장이 해당 문제 맥락과 정확히 관련 있는가"까지 코드만으로 100% 판별하지는 못합니다.
- 그래서 글자 대조 위에 LLM 재확인, P0 Critic 교차 감사, 사람 검토 목록을 겹쳐 두었고, 현재 `83% (52/63)`도 Claude 초안 판정 상태라 팀의 사람 라벨 확인을 진행 중입니다.

### Q4. Claude Code나 Codex 자체 메모리 · 플랜 모드가 계속 좋아지고 있는데, Seedup이 살아남을 수 있나요?
- 그 점을 위험 요소로 문서(계획 6절)에 명시해 두었습니다. 그럼에도 오래 남는 차이는 세 가지입니다.
  1. **도구 중립성:** Claude Code에서 Codex로 바꿔도 서버에 목표와 결정 기억이 남습니다.
  2. **바깥에서의 교차 판정:** 코드를 쓴 모델이 같은 세션에서 스스로 "완료"를 판정하는 구조적 한계를, 다른 계열 모델과 실제 GitHub 커밋 · CI 결과로 깹니다(단계 2 계획).
  3. **원문 근거 체인:** 프롬프트에서 출발하지 않고 실제 개발자 불만 원문(`E-n`)과 경쟁 도구 확인에서 출발합니다.

### Q5. 2단 검증(단계 2 계획)을 왜 GitHub Actions 안에서 안 돌리고 Seedup 서버에서 돌리나요?
- 사용자 저장소의 GitHub Actions 워크플로 파일은 개발 에이전트가 직접 수정하거나 검사를 느슨하게 바꿀 수 있기 때문입니다.
- 그래서 판정 로직은 Seedup 서버에만 두고, GitHub API로 실제 커밋 SHA와 CI 결과만 읽어 판정하도록 설계했습니다(계획 1절 · 3-4절).

### Q6. 2인이 여러 AI 에이전트를 쓰면서 코드 충돌이나 품질 저하는 없었나요?
- 초기에 문서가 흩어지고 에이전트가 동시에 같은 파일을 건드리는 문제를 겪었고, 이를 해결하려고 `docs/supervisor-plan.md`(단일 최상위 계획 · 단계별 파일 소유표), `CONTRIBUTING.md`(브랜치 · PR · 공용 파일 · 문서 수정 권한 규칙), `docs/decisions.md`를 정비해 PR 리뷰와 CI 검증을 거치도록 바꿨습니다.
