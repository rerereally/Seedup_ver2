# 무엇을 만들지부터 코드까지: 기능 계획 (일일 리서치 · 진행 상황 · 코드 추적 · 코드 그래프)

작성일 2026-11-19. 아직 구현 전인 계획입니다.

A~I 아홉 기능은 모두 하나의 목표를 위한 것입니다. **원문 → PRD → 코드**를 끊기지 않게 잇는 것입니다. 지금은 근거 추적이 PRD에서 멈춰 있는데, 이것을 코드까지 늘립니다. 그러면 "이 코드가 왜 있는가"를 원문 인용까지 거슬러 올라가 확인할 수 있습니다.

의존 관계는 이렇습니다.
- **A → B → C** 순서로 쌓입니다.
- **F와 G**는 B의 파일-기능 연결표가 있어야 합니다.
- **H**는 A와 B가 있어야 하고, C가 있으면 더 좋아집니다.
- **D, E, I**는 따로 만들 수 있습니다.

권장 순서는 A → B → F → H → C → G → I이고, D와 E는 여유가 있을 때 합니다.

J는 고리의 맨 앞, 즉 무엇을 만들지 고르는 단계를 다룹니다. A~I와 독립적이라 따로 진행해도 됩니다. 예외는 J-6의 MCP 카드 하나입니다. 이 카드는 고른 기회에서 바로 작업으로 넘어갈 때 H의 `get_next_task`를 씁니다. 그 밖에도 J의 "나에게 맞는 순서"는 C의 코드 그래프가 있으면 더 정확해지고, "다른 사람이 만든 것"은 I와 이어집니다.

새 MCP 도구는 모두 아래 "새 MCP 도구 공통 규칙"을 따릅니다.

## A. 기능별 진행 상황 (기반)

- **보여 주는 것:** PRD 기능(`F-n`)마다 지금 상태와 바뀐 이력을 보여 줍니다. 상태는 대기 · 작업 중 · 개선 중 · 완료 · 막힘 · 다시 확인 필요, 여섯 가지입니다. "다시 확인 필요"는 에이전트가 보고하는 상태가 아닙니다. F가 자동으로 붙입니다.
- **지금 있는 것:** `build_progress` 테이블과 MCP 도구 `mark_feature_done`이 있습니다. 상태는 완료와 미완료 두 가지뿐이고, 미완료로 바꾸면 행이 지워집니다(`lib/opportunities/build-progress.ts`).
- **바꿀 것:**
  - `build_progress`에 `status`와 `updated_at` 칸을 추가합니다. 상태 이력 테이블도 새로 만듭니다.
  - MCP 도구 `mark_feature_done`을 `update_feature_status`로 넓힙니다. 기존 이름은 호환을 위해 남겨 둡니다.
  - `AGENTS.md` 내보내기에 "기능을 시작할 때와 끝낼 때 상태를 보고하라"는 규칙을 넣습니다. Claude Code 사용자는 훅으로 자동 보고하게 할 수 있습니다.
  - 상태가 막힘으로 바뀌면 기존 `notify_webhook`으로 알림을 보냅니다.
- **신뢰 장치:** 에이전트가 말한 상태와 검증된 상태를 나눠 표시합니다(예: "에이전트는 완료라고 함 / 완료 기준 검증 전"). 지금도 `mark_feature_done`은 수락 기준마다 확인 결과와 근거(`checks`)를 받아, 모두 통과해야 완료로 기록합니다. 다만 이것은 에이전트의 자기 보고입니다. 서버가 diff로 다시 확인하는 일은 B가 맡습니다.

## B. 코드에서 원문까지 추적

- **보여 주는 것:** 커밋과 파일이 어떤 기능, 요구사항, 원문 인용에 연결되는지 보여 줍니다.
- **방법:**
  - `AGENTS.md` 규칙으로 커밋 메시지에 `Implements F-03 (R-2 ← E-5, E-9)` 같은 표기를 남기게 합니다.
  - MCP 도구 두 개를 추가합니다.
    - `link_commit`: 커밋과 그 커밋이 바꾼 파일 목록을 기록합니다.
    - `verify_feature`: diff를 `F-n`의 완료 기준(6가지 준비 슬롯 중 "완료 기준")과 대조합니다.
- **결과:** 파일과 기능을 잇는 연결표(가칭 `feature_files`)가 생깁니다. C에서 그래프에 기능과 원문을 겹쳐 그릴 때 이 표를 씁니다.

## C. 코드 그래프 (graphify 연동)

- **graphify가 하는 일:** tree-sitter로 코드를 분석해 파일과 함수의 관계를 그래프로 만듭니다. 코드 분석에는 LLM을 쓰지 않습니다. 결과는 `graph.json`, `graph.html`, `GRAPH_REPORT.md`로 나옵니다. MCP 서버로 쓸 수도 있습니다. 라이선스는 MIT와 Apache-2.0입니다.
- **직접 만들지 않는 이유:** 이미 잘 만든 도구가 있습니다. 게다가 graphify는 Python으로 돌아가서 Seedup 서버(Cloudflare Workers)에서는 실행하기 어렵습니다.
- **구조:**
  1. 사용자의 에이전트가 사용자 컴퓨터의 저장소에서 graphify를 실행합니다.
  2. 만들어진 `graph.json`을 MCP 도구 `upload_code_graph`로 Seedup에 올립니다.
  3. Seedup은 그 그래프 위에 기능(`F-n`), 상태(A), 원문(`E-n`)을 겹쳐 그립니다. 겹쳐 그릴 때 B의 연결표를 씁니다.
- **Seedup만의 가치:** 그래프 자체는 graphify도 그려 줍니다. Seedup이 더하는 건 노드마다 붙는 정보입니다.
  - 이 파일 묶음이 F-03을 구현하고, F-03은 원문 E-5와 E-9의 불만을 해결한다.
  - 지금 상태는 개선 중이다.
  - 아직 연결된 코드가 하나도 없는 불만은 구현이 안 된 빈 곳으로 보여 준다.
- **주의할 점:**
  - 업로드는 사용자가 직접 켰을 때만 합니다. 그래프에는 파일 이름과 구조가 들어가고, 코드 본문은 올리지 않습니다.
  - 그래프가 크면 DB 칸이 아니라 Supabase Storage에 저장합니다.
- **확인 필요:** `graph.json` 형식과 실제 크기는 직접 실행해 보지 않았습니다.

## D. 근거가 바뀌면 PR 보내기

- **보여 주는 것:** `watch.ts`가 새 원문이나 새 경쟁 도구를 찾으면, 메일만 보내던 것을 넘어 사용자 저장소에 PR을 엽니다. PR에는 `AGENTS.md`와 스펙의 바뀐 부분을 담습니다.
- **PR 예시:**
  - "새 증언 E-14가 R-3의 수락 기준을 바꿉니다."
  - "경쟁 도구 X가 F-2를 출시했습니다. 빈틈 상태가 open에서 narrowing으로 바뀝니다."
- **필요한 것:** 저장소에 쓸 수 있는 GitHub App 권한이 필요합니다. 바뀐 부분은 `spec-diff.ts`를 재사용해 만듭니다.

## E. 미리 봉인한 예측 성적표

- **보여 주는 것:** 기준을 통과한 기회마다 그 시점의 예측(예: "N일 안에 관련 도구가 나온다")을 해시로 봉인해 공개 저장소에 커밋합니다. 나중에 실제로 맞았는지 자동으로 채점합니다.
- **이유:** 지금의 적중 기록(28개 중 13개, 46% · 중간값 52일, `docs/final-report.md` 기준이며 지금 숫자는 확인 필요)은 지나간 데이터로 계산한 숫자라서 "끼워 맞춘 것 아니냐"는 반박에 약합니다. 미리 봉인해 두면 사후 해석이 아니라 사전 등록된 예측이 됩니다.
- 다른 기능과 독립적이고, 만드는 비용도 가장 적습니다.

## F. 완료된 기능이 깨졌는지 감지하기

- **해결하는 문제:** 에이전트가 새 기능을 만들다가 이미 끝난 기능을 망가뜨리는 일은 바이브 코딩에서 가장 흔한 사고입니다.
- **방법:**
  - B의 파일-기능 연결표를 씁니다.
  - "완료" 상태인 기능(예: F-03)이 쓰는 파일이 나중 커밋에서 바뀌면, 그 기능을 자동으로 **"다시 확인 필요"** 상태로 돌립니다.
  - 에이전트에게는 MCP 응답으로 "F-03의 완료 기준을 다시 검증하라"고 알립니다.
- **새로 만들 것:** 연결표만 있으면 규칙 하나로 만들 수 있습니다. 상태는 A의 여섯 가지 중 "다시 확인 필요"를 씁니다.

## G. PRD에 없는 작업 경고하기

- **해결하는 문제:** 에이전트는 시키지 않은 기능을 만들거나 엉뚱한 곳을 고칩니다.
- **방법:** 어떤 `F-n`에도 연결되지 않은 커밋이나 파일 변경이 쌓이면 **"근거 없는 작업"**으로 표시합니다.
- **Seedup다운 이유:** 지금도 증언 근거가 없는 요구사항은 가설(H-n)로 따로 둡니다. 이 원칙을 코드 단계까지 넓히는 것입니다.
- **주의할 점:** 설정 파일, 리팩터링, 테스트처럼 기능에 묶이지 않는 정상적인 작업도 있습니다. 그래서 막지는 않고 표시만 합니다. 사용자가 "기능 아님"으로 정리할 수 있게 합니다.

## H. 다음 할 일과 필요한 맥락을 한 번에 건네기

- **해결하는 문제:** 에이전트는 새 세션마다 무엇을 해야 하고 어떤 파일을 봐야 하는지 처음부터 다시 찾습니다. 그만큼 시간과 토큰이 낭비됩니다.
- **방법:** MCP 도구 `get_next_task`를 추가합니다.
  - 남은 기능 중에서 원문 근거가 많고, 앞선 기능에 막혀 있지 않은 것을 하나 고릅니다.
  - 고른 기능의 원문 인용, 완료 기준(6가지 준비 슬롯), 관련 파일을 한 묶음으로 건넵니다. 관련 파일은 B의 연결표와 C의 코드 그래프에서 찾습니다.
  - F에서 "다시 확인 필요"가 된 기능이 있으면 그것을 먼저 건넵니다.
- **결과:** Seedup이 PRD를 써 주는 도구에서 에이전트의 작업 반장이 됩니다. 매일 열어 볼 이유가 생깁니다.

## I. 출시 후 반응을 다시 증거로 넣기

- **해결하는 문제:** 지금 고리는 코드에서 끝납니다. 그 코드가 원래 불만을 실제로 해결했는지는 모릅니다.
- **방법:**
  - `/try` 대기자 명단 가입 수를 기능 단위 지표로 PRD에 붙입니다.
  - 원문 작성자에게 직접 보낸 답장에 대한 반응도 PRD에 넣습니다. 답장 초안은 `outreach.ts`가 만듭니다.
  - 들어온 반응은 직접 들은 말과 같은 종류의 증거로 PRD에 담고, 검증 기준 숫자에는 세지 않습니다.
- **주의할 점:** 답장은 절대 자동으로 올리지 않습니다. 스팸이 되고 플랫폼에서 차단당합니다. 지금처럼 사람이 직접 보내는 초안으로만 둡니다.
- **결과:** 원문 → PRD → 코드 → **다시 원문 작성자**로 고리가 닫힙니다.

## J. 인사이트를 "뭘 만들지 고르는 곳"으로 업그레이드 (일일 시장 리서치)

바이브 코더와 개발자의 첫 고민은 "무엇을 만들까"입니다. 이 고민을 위한 새 페이지를 만들면 인사이트 페이지(`/newsletter-preview`, `/opportunities/[slug]`)와 거의 그대로 겹칩니다. 그래서 새로 만들지 않고 인사이트를 업그레이드합니다.

### J-0. 먼저 막히는 곳: 고를 거리가 적음

고정 스냅샷(`lib/opportunities/data/snapshot.json`)은 2026-11-19 저녁에 운영 DB에서 다시 내보냈습니다(`scripts/export-snapshot.ts`).
- 처음 이 문서를 쓸 때는 문제 44개 중 2개만 기준을 통과했고, 규모 추정(`build`)은 0/44였습니다.
- 다시 내보낸 뒤에는 문제 37개 중 13개가 기준을 통과했고, 규모 추정은 37개 모두 채워져 있습니다.

그래서 "고를 거리가 1~2개"라는 문제는 많이 줄었습니다. 그래도 매일 비교해 보여 주려면 문제 수가 더 많아야 하므로, 데이터 양을 늘리는 일은 계속합니다.
- 새 플랫폼을 붙이지 않습니다. 지금 있는 9곳에서 검색어와 수집 기간을 넓혀 문제 수를 늘립니다.
- 규모 추정(`fillBuildEstimates`)이 실제로 채워지는지 확인합니다.
- "원문 모으는 중"인 문제도 기준 미달이라는 표시를 단 채 고를 거리로 보여 줍니다.

**확인 필요:** 스냅샷은 공개 문제만 담습니다. 엔진이 매일 돌며 숫자가 바뀌므로, 화면을 만들기 전에 운영 DB 숫자를 다시 확인합니다.

### J-1. 오늘의 시장 리서치

**이미 매일 돌고 있는 것**
- `scheduled-ingest.yml`(cron 21:00 UTC): 원문 9곳, 기존 도구, 읽을거리를 수집합니다.
- `opportunity-engine.yml`(cron 22:00 UTC): 문제를 묶고, 검증하고, 규모를 추정해 DB에 저장합니다(`--persist`). 최근 10회 중 9회 성공했고, 한 번에 14~46분 걸렸습니다.
- 문제마다 실행할 때마다 원문 수, 플랫폼 수, 경쟁 도구 수, 상태가 `history`에 쌓입니다.

리서치 자체는 이미 매일 돌고 있습니다. 새로 만들 것은 어제와 오늘을 비교해서 보여 주는 화면입니다. 인사이트 맨 위에 다음 네 가지를 둡니다.

1. **어제와 달라진 것:** `history`의 숫자를 비교해 계산하므로 모델이 지어낼 여지가 없습니다.
   - 새로 나타난 불만
   - 원문이 빠르게 늘어나는 문제(수요 상승)
   - 오늘 검증 기준을 넘은 문제
   - 새 경쟁 도구가 나와 빈틈이 닫히는 문제(open → narrowing)
2. **이번 주 수요가 몰리는 분야:** 문제를 키워드와 직군(`audience`)으로 묶어 분야별 증가량을 보여 줍니다.
3. **오늘 나에게 추천하는 것 하나:** J-2의 개인화로 고릅니다.
4. **짧은 요약 글:** 모델은 위 숫자를 요약하는 문단만 씁니다. 인용은 원문 글자 대조(`isVerbatimQuote`)를 통과한 것만 씁니다. "점수는 저장된 수치로만 계산한다"는 지금 원칙과 같습니다.

**주의할 점**
- **변화가 적은 날:** 문제 수가 적으면 하루 사이 변화가 없는 날이 많습니다. 그런 날에는 기간을 "최근 7일"로 자동으로 넓혀서 빈 화면이 나오지 않게 합니다. 가장 큰 위험입니다.
- **신호와 예측의 구분:** "원문이 늘고 있다"는 사실이지만 "그래서 돈이 된다"는 가설입니다. 화면에서는 신호라고만 부릅니다. E(미리 봉인한 예측)가 있으면 신호의 과거 적중률을 함께 보여 줍니다.
- **리포트 시각:** cron은 21~22시(UTC)로 잡혀 있습니다. 그런데 GitHub Actions 실행 기록에 찍힌 시각은 01~04시(UTC)입니다. 그대로라면 결과는 한국 시간 오전 10시~오후 1시쯤 나옵니다. 왜 늦게 찍히는지는 확인하지 못했습니다(확인 필요). 아침 리포트를 원하면 원인을 먼저 확인하고, 그다음 시작 시간을 당깁니다.

### J-2. 나에게 맞는 순서로 보여 주기

- 지금은 모든 사람에게 같은 목록이 같은 순서(검증 여부, 원문 수)로 보입니다.
- 사용자의 기술 스택을 GitHub 저장소(`lib/seeds/github.ts`)나 C의 코드 그래프에서 알아냅니다. 쓸 수 있는 시간도 받습니다.
- 둘을 합쳐 "이번 주말에 내가 만들 수 있는 것" 순서로 정렬합니다.

### J-3. 다른 사람이 이미 만든 것 보여 주기

- `built_url`("만들었어요" 링크)은 이미 저장되고 있습니다.
- 문제 상세와 목록에 "이 불만으로 N명이 만들었다"를 보여 줍니다. 많이 만들었으면 피하라는 신호이고, 결과가 좋았으면 해 볼 만하다는 증거입니다.
- 링크를 보여 주는 것은 만든 사람이 공개를 켠 경우만입니다.

### J-4. 후보 두세 개 비교하기

- 고민하는 사람은 후보 몇 개를 저울질합니다.
- 원문 수, 경쟁 도구 수, 규모, 첫 10명 후보를 나란히 놓은 비교 화면을 만듭니다.

### J-5. 새로 만들기와 내 프로젝트의 다음 기능을 한곳에

- 기존 프로젝트의 다음 기능 제안은 `/seeds`에 따로 있습니다.
- 인사이트 안에 **"새로 만들기 / 내 프로젝트의 다음 기능"** 두 갈래를 두어, 무엇을 만들지를 한곳에서 고르게 합니다.

### J-6. 보여 주는 곳

- **인사이트 페이지:** 전체 리서치와 비교 화면을 보여 줍니다.
- **에이전트 앱 안의 MCP Apps 카드:** "내 스택에 맞는 오늘의 기회"를 보여 줍니다. 고르는 순간 PRD를 만들고 H의 `get_next_task`로 바로 작업에 들어갑니다.
- **메일:** 원하는 사람에게만 매일 아침 보냅니다. 주간 뉴스레터(`lib/newsletter`)를 매일용 가벼운 버전으로 재사용합니다.

## 넣지 않기로 한 것

- **토큰·비용 추적, 실시간 파일 편집 로그:** 에이전트 도구들이 이미 기본으로 보여 줍니다.
- **Seedup 안의 채팅창:** 사용자를 에이전트 앱 밖으로 끌어냅니다. 아래 "어디서 보여 줄까"의 방향과 반대입니다.
- **AI 페르소나 인터뷰 같은 생성형 기능:** "AI는 근거를 지어낸다"는 Seedup의 출발점과 부딪힙니다.
- **새 플랫폼(데이터 소스) 추가:** 이미 9곳이라 더 늘려도 효과가 작습니다. 문제 수가 부족한 건 지금 있는 9곳에서 검색 범위를 넓혀 해결합니다(J-0).

## 어디서 보여 줄까

웹과 에이전트 앱 둘 다 씁니다. 대신 둘의 역할을 나누고, IDE 확장 프로그램은 따로 만들지 않습니다.

| 보여 주는 곳 | 역할 | 방법 |
|---|---|---|
| 에이전트 앱 안 (Claude, ChatGPT, VS Code Copilot, Cursor 등. 연결 설정은 `/agents`에서 Claude Code, Claude 앱, Codex, Cursor, VS Code, Antigravity, Gemini CLI, Windsurf, ChatGPT 아홉 가지를 안내) | 작업 중에 흘끗 보는 정보: 지금 진행 상황, 이번 커밋이 해결한 불만, 내 스택에 맞는 오늘의 기회 | **MCP Apps**: MCP 도구의 응답이 대화창 안에 작은 화면으로 뜹니다 |
| 웹 (인사이트 페이지, `/prd`, 새 프로젝트 지도 화면) | 오래 들여다보는 정보: 오늘의 시장 리서치와 후보 비교, 전체 코드 그래프, 이력, 공유, 시연 | 지금 있는 웹 앱을 확장합니다 |
| MCP Apps를 지원하지 않는 곳 (터미널 등) | 짧은 글 요약과 웹 링크 | 지원하지 않는 호스트에서는 MCP Apps 응답이 자동으로 글로 바뀝니다 |

이렇게 나누는 이유는 네 가지입니다.

- **MCP Apps(`io.modelcontextprotocol/ui`)는 이미 표준입니다.** 2026년 1월에 첫 공식 MCP 확장으로 나왔고, 여러 에이전트 앱이 지원합니다. 그래서 MCP 서버 하나만 고치면 VS Code와 Cursor 확장을 따로 만들지 않아도 됩니다.
- **바이브 코더는 에이전트 앱을 떠나지 않습니다.** 흘끗 볼 정보는 대화창 안에 있어야 실제로 봅니다.
- **큰 그래프는 대화창에 담기 어렵습니다.** 전체 지도, 공유, 심사 시연은 웹이 맡습니다.
- **시연 흐름:** Claude 대화창에서 기능을 완료하면 그 자리에 "E-5 불만 해결됨" 카드가 뜹니다. 카드를 누르면 웹에서 코드 그래프 전체가 열립니다.

**확인 필요:**
- Claude Code CLI(터미널)가 MCP Apps를 지원하는지는 확인하지 못했습니다. 지원하지 않으면 글 요약과 링크로 보여 줍니다.
- 앱마다 지원 범위가 다릅니다. 구현 전에 공식 지원 목록을 다시 확인해야 합니다.

### MCP 화면을 띄우는 방식 (구현안, 2026-11-19)

MCP Apps는 도구 응답 옆에 작은 HTML 화면을 띄우는 표준 확장입니다. 지원하는 곳은 Claude(웹·데스크톱), VS Code Copilot, Microsoft 365 Copilot, Goose 등입니다. Claude Code, Codex, Gemini CLI 같은 터미널 도구는 화면을 그리지 않습니다.

**서버에서 할 일 (lib/mcp/server.ts)**
1. 화면을 붙일 도구 정의에 `_meta.ui.resourceUri: "ui://seedup/<이름>"`을 넣습니다.
2. `resources/list`와 `resources/read`가 그 주소의 HTML 한 장을 돌려주게 합니다. 지금 `resources/list`는 빈 목록만 돌려줍니다. HTML에는 JS와 CSS를 모두 담고, 외부 주소는 `_meta.ui.csp`에 적은 곳만 씁니다.
3. 도구 결과에 화면이 읽을 JSON(`structuredContent`)을 더합니다. 지금 보내는 글(`content`)은 그대로 둡니다. 화면을 못 그리는 도구는 이 글을 보여 줍니다.
4. 화면은 호스트와 postMessage(JSON-RPC, `ui/` 메서드)로 통신합니다. 결과를 받아 그리고, 버튼을 누르면 `tools/call`로 다른 도구를 부릅니다. 의존성 없이 직접 구현할 수도 있고, `@modelcontextprotocol/ext-apps`의 `App` 클래스를 써도 됩니다.

**먼저 만들 화면 3장**
| 도구 | 화면 | 버튼 |
|---|---|---|
| `search_opportunities` | 기회 카드 3개: 문제, 원문 수, 플랫폼, 빈틈 상태 | "이걸로 PRD 만들기" → `generate_verified_prd` |
| `generate_verified_prd` | PRD 요약: 기능 F-n 목록과 기능마다 붙은 원문 인용 수 | "웹에서 전체 보기" (`/prd?opportunity=`), "체크리스트" → `get_build_checklist` |
| `get_build_checklist` | 진행 막대: 기능별 완료·남음, 수락 기준 | 완료 처리는 에이전트가 `mark_feature_done`으로 합니다. 화면에서는 하지 않습니다 |

**시연 흐름:** Claude 웹에 커넥터를 연결합니다(`/agents`의 "Claude 앱", 주소에 토큰을 넣는 방식). "AI 에이전트 관련 기회 찾아줘"라고 하면 기회 카드가 뜹니다. 카드에서 PRD를 만들고, 같은 PRD를 Claude Code나 Codex에서 체크리스트로 받아 구현합니다. 다시 Claude 웹에서 진행 막대가 바뀐 것을 봅니다.

**주의할 점**
- 화면이 없어도 모든 흐름이 글만으로 끝나야 합니다. 화면은 덧붙이는 것입니다.
- HTML은 서버 코드와 같은 저장소에서 빌드해 한 파일로 넣습니다. 따로 배포하지 않습니다.
- **확인 필요:** 구현 전에 [MCP Apps 명세](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)에서 리소스 MIME 형식과 `ui/` 메서드 이름을 다시 확인합니다. Claude 데스크톱에서 실제로 그려지는지도 직접 확인합니다.

## 새 MCP 도구 공통 규칙

`link_commit`과 `upload_code_graph`는 파일 경로와 코드 구조를 Seedup으로 올립니다. 비공개 저장소에서는 파일 경로도 민감한 정보입니다. 그래서 위 표의 새 도구는 모두 아래 규칙을 따릅니다.

- **사용자가 켰을 때만:** 커밋 정보와 코드 그래프는 사용자가 프로젝트마다 직접 켰을 때만 올립니다. 코드 본문은 올리지 않습니다.
- **들어온 값 검사:** 올라오는 값은 서버에서 크기를 제한하고 형식을 검사합니다(`graph.json`, 파일 목록, 커밋 메시지). 형식이 맞지 않으면 저장하지 않고 거절합니다.
- **사용량 한도:** 기존 MCP 사용량 한도(`consume_ai_usage_for`)를 똑같이 적용합니다. 모델을 부르는 도구(`verify_feature`, `get_daily_research`의 요약)는 실패하면 사용량을 돌려줍니다(`release_ai_usage`).
- **권한:** MCP 토큰(`sdp_...`)으로는 그 토큰 주인의 PRD와 프로젝트만 읽고 쓸 수 있습니다. 새 테이블에도 `build_progress`처럼 본인 행만 읽는 RLS를 걸고, 쓰기는 서버만 합니다.

| 기능 | 지표 예시 |
|---|---|
| A | 상태 보고가 한 번이라도 들어온 PRD의 비율 |
