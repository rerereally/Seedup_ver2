# Seedup 개선 계획서

작성일 2026-11-14. 기준 코드는 `21dcfa0`이고, 이 문서를 쓰면서 바꾼 코드는 없습니다.

## 0. 목표와 원칙

**목표:** 국내 해커톤(2026 Winter AI Bootcamp Awards)과 세계 규모 해커톤에서 모두 1등을 다툴 수 있는 완성도.

어떤 계획도 1등을 보장하지는 못합니다. 다만 큰 대회에서 이기는 프로젝트는 공통점이 뚜렷하고, 이 계획은 그 공통점에 맞춰져 있습니다.

1. **한 문장으로 설명되는 차별점이 있다.**
   - Seedup의 차별점: "기획서의 모든 줄이 실제 개발자의 증언 원문으로 거슬러 올라간다."
   - Manyfast는 기획서를 목표에 연결합니다. Seedup은 기획서를 검증된 증언에 연결합니다.
2. **데모가 한 번도 끊기지 않는다.** 라이브 LLM이 실패해도 화면이 멈추지 않아야 합니다.
3. **숫자로 증명한다.** 적중 기록(backtest), 검증을 통과한 인용 비율, 근거 수 같은 실제 수치를 보여줍니다.
4. **심사위원이 직접 만져볼 수 있다.** 공개 링크로 열리고, 영어로도 읽히고, 휴대폰에서도 동작해야 합니다.

일정(며칠 안에 끝낸다)은 이 문서의 기준이 아닙니다. 순서는 의존 관계와 위험도로 정했습니다.

## 2. 코드 감사에서 새로 찾은 문제

명세서에 없던 문제입니다. 사용자가 많지 않은 서비스(해커톤 심사 기간에 수십~수백 명이 동시에 접속)를 기준으로 판단했습니다.

### 꼭 고칠 것

**N1. 아이디어 평가의 근거 검색(RAG)이 새 콘텐츠를 영영 찾지 못함** (`app/api/ideas/evaluate/route.ts:86`, `lib/ingest/rag.ts:150`)
- **무슨 코드인가:** 아이디어를 평가할 때 비슷한 뉴스·논문·레포를 임베딩(문장을 숫자 벡터로 바꾼 것)으로 찾아서 근거로 붙입니다.
- **문제:** 임베딩을 만드는 `syncMissingEmbeddings`를 부르는 곳이 단 한 군데이고, 그마저 `syncMissing: false`로 꺼져 있습니다. 주석에는 "수집 과정이 채운다"고 쓰여 있지만, 수집 라우트 어디에서도 임베딩을 만들지 않습니다. 그래서 새로 수집한 콘텐츠는 평가 근거로 한 번도 잡히지 않습니다.
- **해결:** 수집이 끝날 때 `syncMissingEmbeddings`를 부르는 단계(`/api/ingest/embeddings`)를 추가하고 `/api/ingest/all` 순서 맨 끝에 넣습니다. 쌓여 있는 데이터는 한 번만 돌리는 백필 스크립트로 채웁니다.
- **고치지 않으면:** "RAG 기반 평가"라고 소개해도 실제로는 근거가 0건으로 나옵니다. 심사위원이 직접 해보면 바로 드러납니다.

**N2. 어드민 "전체 수집"이 실패해도 항상 성공이라고 표시됨** (`app/actions/ingest.ts:44-61`)
- **무슨 코드인가:** 어드민 버튼을 누르면 9개 수집기를 차례로 실행합니다.
- **문제:** `runManualIngestNoRedirect`가 결과를 버리기 때문에, 단계가 모두 실패해도 마지막에 `status=success`로 이동합니다.
- **해결:** 각 단계 결과를 모아 하나라도 실패하면 `failed`와 실패한 단계 이름을 넘깁니다.
- **고치지 않으면:** 데모 직전에 수집이 실패해도 알아채지 못하고, 빈 데이터로 발표하게 됩니다.

**N3. 조회수 증가가 동시 요청에서 사라짐** (`lib/engagement.ts:10-20`)
- **무슨 코드인가:** 상세 페이지를 열면 조회수를 1 올립니다.
- **문제:** 현재 값을 읽고 +1 해서 다시 쓰는 방식이라, 두 사람이 동시에 열면 한 번만 올라갑니다. 로그인 없이 누구나 이 API를 호출할 수도 있습니다.
- **해결:** `update ... set view_count = view_count + 1`을 한 번에 실행하는 SQL 함수(RPC)로 바꿉니다. 명세서 버그 06(+1 표시 불일치)과 함께 고칩니다.
- **고치지 않으면:** 심사 기간처럼 접속이 몰릴 때 조회수가 실제보다 적게 나옵니다.

**N4. 로그인 없이 누구나 공용 LLM 한도를 다 써버릴 수 있음** (`app/api/seeds/route.ts`, `app/api/opportunities/match/route.ts`)
- **무슨 코드인가:** 씨앗 화면의 아이디어 제안과 기회 검색이 무료 OpenRouter 모델을 부릅니다.
- **문제:** 요청 제한이 서버 인스턴스 메모리에만 있습니다. Cloudflare는 인스턴스가 여러 개라서 사실상 제한이 걸리지 않습니다. 한 사람이 스크립트로 두드리면 PRD 생성까지 함께 멈춥니다.
- **해결:** LLM을 부르는 `step=ideas`는 로그인을 요구하고 `consumeDailyUsage`를 적용합니다. 임베딩만 쓰는 `match`는 지금처럼 두되 결과 캐시를 유지합니다.
- **고치지 않으면:** 발표 도중 누군가 장난으로 호출하면 데모 전체가 503 오류를 냅니다.

**N5. 수집 비밀값을 URL 쿼리로도 받음** (`lib/ingest/auth.ts:12`)
- **무슨 코드인가:** 수집 API는 비밀값이 있어야 실행됩니다.
- **문제:** `?secret=...`도 허용합니다. URL은 Cloudflare 로그, 브라우저 기록, 리퍼러 헤더에 그대로 남습니다.
- **해결:** 쿼리 파라미터는 받지 않고, 헤더(`x-ingest-secret`, `Authorization`)만 받습니다.
- **고치지 않으면:** 로그를 본 사람이 수집을 마음대로 돌려 LLM 한도를 소진시킬 수 있습니다.

### 고치면 좋은 것

**N6. 수집 경로 목록이 두 곳에 복사되어 있음** (`app/api/ingest/all/route.ts:7`, `app/actions/ingest.ts:9`)
- 한쪽만 바꾸면 어드민과 크론이 서로 다른 설정으로 수집합니다. `lib/ingest/steps.ts` 하나로 합칩니다.

**N7. 수동 뉴스레터 발송이 서버 액션 하나에서 전원에게 보냄** (`app/actions/newsletter.ts`)
- 구독자 한 명당 600ms를 기다리므로 구독자가 100명이면 1분이 넘고, 요청 시간 제한에 걸려 중간에 끊깁니다.
- `claimSend` 덕분에 다시 눌러도 중복 발송은 되지 않습니다. 다만 "몇 명에게 보냈는지"가 화면에 나오지 않습니다. 결과를 발송 기록에 남기고, 끊기면 이어서 보내도록 합니다.

**N8. 사용자가 보낸 PRD 마크다운을 그대로 저장함** (`app/api/opportunities/dossiers/route.ts:29`)
- 지금은 본인만 보므로 위험하지 않습니다. 하지만 명세서 05(PRD 전문 보기)와 아래 공개 공유 링크를 만들면 다른 사람에게 보여지게 됩니다.
- 마크다운을 HTML로 바꿀 때 원시 HTML은 허용하지 않아야 합니다. 서버가 만든 PRD만 저장하는 방식이 가장 안전합니다.

**N9. 아이디어 평가 횟수 제한이 동시 요청에 뚫림** (`app/api/ideas/evaluate/route.ts:73-82`)
- 개수를 센 다음 나중에 저장하므로, 동시에 20번 보내면 한도를 넘깁니다.
- PRD와 같은 `consume_ai_usage`로 바꾸고, 실패하면 돌려줍니다(명세서 04와 같은 수정).

**N10. 메인 뉴스레터에 구독 해지 링크가 없음** (`lib/newsletter/email.ts:93`)
- 기회 다이제스트에는 `/profile` 링크가 있지만, 메인 뉴스레터에는 문구만 있습니다. 정보통신망법상 광고성 메일에는 수신거부 방법을 명확히 안내해야 합니다. 링크 한 줄을 추가합니다.

## 4. Manyfast 기능 설계 (21~24)

핵심 원칙: **모든 요구사항·기능·화면 ID는 증언 ID를 하나 이상 갖는다.** 근거가 없는 항목은 가설로 따로 표시합니다. 이 한 가지가 Manyfast와 Seedup을 가르는 선입니다.

### 4.1 데이터 모델 (`lib/opportunities/prd.ts`의 `PrdDraft` 확장)

```ts
type Spec = {
  evidence: Evidence[];                 // 이미 있음. 각 항목의 id가 E-1, E-2… 로 표시됨
  requirements: Array<{ id: 'R-01'; text: string; evidenceIds: string[] }>;
  features: Array<{ id: 'F-01'; requirementIds: string[]; title: string; slots: ReadinessSlots }>;
  screens: Array<{ id: 'S-01'; featureIds: string[]; name: string; components: string[] }>;
  flow: string;                         // Mermaid flowchart 코드
  hypotheses: Array<{ id: 'H-01'; text: string }>; // 이미 있음
};

type ReadinessSlots = {                 // 22번: 개발 준비 슬롯 6개
  inputs: string[];        // ① 입력과 상태 조건
  rules: string[];         // ② 비즈니스 규칙
  errors: string[];        // ③ 예외와 오류 처리
  access: string[];        // ④ 권한과 접근 제어
  data: string[];          // ⑤ DB와 데이터 요건
  done: string[];          // ⑥ 테스트와 완료 기준
};
```

- `normalizePrd`가 서버에서 검증합니다.
  - 존재하지 않는 증언 ID를 가리키는 항목은 버립니다.
  - 근거가 없는 R은 H(가설)로 옮깁니다.
  - 고아 F·S(위 단계와 연결되지 않은 항목)는 버립니다.
- 이 검증 로직은 단위 테스트로 고정합니다.
- 무료 모델이 긴 JSON을 자주 잘라 먹기 때문에, 생성은 두 번에 나눕니다.
  1. R·F·S 뼈대를 만듭니다.
  2. F마다 개발 준비 슬롯을 채웁니다. 이 호출은 F별로 따로 해서, 하나가 실패해도 나머지는 유지됩니다.

### 4.2 21번 계층 연결 화면 (`components/opportunity-stage/PrdBuilder.tsx`)

- 탭은 네 개입니다: **증언 → 요구사항 → 기능 → 화면·플로우**.
- 어느 항목이든 누르면 위아래로 연결된 항목이 함께 강조됩니다. 증언은 원문 인용과 출처 링크가 펼쳐집니다. 이 장면이 발표의 핵심 시연입니다.
- 와이어프레임 이미지는 만들지 않습니다. S의 컴포넌트 목록과 Mermaid 유저플로우로 대신합니다.
  - Mermaid 렌더러는 화면을 열 때만 불러옵니다(dynamic import).
  - 새로 추가하는 의존성은 이것 하나입니다.

### 4.3 22번 개발 준비 슬롯

- F 카드마다 슬롯 6개를 접었다 펼 수 있게 보여줍니다.
- 비어 있는 슬롯은 "개발자가 다시 물어볼 질문"으로 표시합니다.
- AGENTS.md·CLAUDE.md·.cursorrules 내보내기에 F별 슬롯을 그대로 넣습니다(20번과 같은 렌더러를 씁니다).
- 프로젝트 빌드 플랜(`app/projects/[id]`)에도 같은 슬롯 구조를 씁니다.

### 4.4 23번 멀티뷰와 대화형 기획 수정

- **뷰 세 가지:**
  - 문서 뷰: 지금의 마크다운
  - IA 트리 뷰: R → F → S 접이식 트리
  - 플로우 뷰: Mermaid
  - 세 뷰 모두 같은 `Spec` 하나를 보여줍니다.
- **수정 바:** "타겟을 초보자로 좁혀줘"처럼 입력하면 `/api/opportunities/prd/revise`가 바꿀 범위(전체, R 하나, F 하나)와 지시문을 받습니다. 바뀐 부분만 다시 생성하고, 4.1의 검증을 다시 통과시킵니다.
  - 증언을 새로 만들어낼 수는 없습니다. 증언 목록은 서버가 고정합니다.
  - 수정 전후 비교(diff)를 보여주고, 되돌리기를 한 단계 지원합니다.
  - 수정 이력은 `evidence_dossiers`에 `spec_json`, `revisions` 열을 추가해 저장합니다.
  - 쿼터는 PRD와 같은 `consume_ai_usage`를 씁니다.

### 4.5 24번 역기획 (Reverse Spec)

- `/seeds`에서 레포를 하나 고르면 다음을 하나의 `Spec`으로 만듭니다.
  - README, 파일 트리 상위 2단계, `package.json`이나 `pyproject` 같은 매니페스트를 읽습니다.
  - 이것으로 기존 구조 IA와 F·S를 만듭니다.
  - 새로 붙일 기능 제안은 연결된 기회의 증언 ID를 갖습니다.
- GitHub 공개 API만 씁니다. 토큰이 필요한 비공개 레포는 다루지 않습니다.
- 결과는 4.2의 같은 화면에서 열리고, 5절 MCP의 `get_spec`으로 IDE에 전달됩니다.

## 6. 실행 순서

각 단계는 앞 단계가 끝나야 의미가 있도록 묶었습니다. 각 단계는 "완료 기준"을 통과하면 끝납니다.

### 1단계 · 끊긴 기능 잇기
대상: 명세서 01~06, N1~N5.
- **완료 기준:**
  - 다른 페이지에서 "평가하기"를 누르면 입력창이 채워진다.
  - 평가를 보관하면 보관함에 보인다.
  - 보관함에서 PRD를 열고 복사할 수 있다.
  - LLM이 실패하면 쿼터가 돌아온다.
  - 새로 수집한 콘텐츠가 평가 근거로 잡힌다.
  - 위 각 항목에 테스트가 하나씩 있다.

### 2단계 · 데이터와 데모 안정성
대상: X1, X2, 07 결정, 08.
- **완료 기준:**
  - 근거 기준을 통과한 기회가 10개 이상이다.
  - 통과한 모든 기회의 인용을 사람이 직접 읽고 확인했다.
  - 데모 동선의 모든 LLM 호출에 대체 결과가 있다.

### 3단계 · Manyfast 기능
대상: 21 → 22 → 20 → 23 → 24 순서. 21·22는 데이터 모델이 같으므로 함께 진행합니다.
- **완료 기준:**
  - PRD 하나에서 증언 → R → F → S → 플로우를 클릭으로 따라갈 수 있다.
  - 내보낸 AGENTS.md를 Claude Code에 넣으면, 슬롯을 근거로 질문 없이 첫 기능을 구현한다.
  - 대화형 수정이 증언을 바꾸지 않는다는 것을 테스트로 확인했다.

### 4단계 · 외부 연결과 세계 대회 대비
대상: X5(MCP), X3(공유 링크), X4(영어), X6(적중 기록).
- **완료 기준:**
  - Claude Code에서 MCP로 연결해 기회 검색부터 PRD 받기까지 된다.
  - QR 코드로 연 공유 링크가 휴대폰에서 깨지지 않는다.
  - 영어로 전환한 화면에서 시연 동선이 전부 영어로 나온다.

### 5단계 · 추천과 뉴스레터
대상: 12~16, N7, N10.
- **완료 기준:** 서로 다른 프로필 두 개로 미리보기를 만들었을 때, 상위 5개 항목 중 3개 이상이 다르다(테스트로 고정).

### 6단계 · 정리
대상: 09, 11, 17, 18, N6, N8, N9, X7.
- **완료 기준:**
  - 모든 상세 페이지가 V2 디자인이다.
  - 어드민에서 수집 진행 상태와 실패 단계가 보인다.
  - E2E 스모크 테스트가 통과한다.

### 발표 준비 (마지막)
- 시연 동선을 고정하고, 녹화 백업 영상을 준비합니다.
- 숫자 슬라이드(수집량, 검증 통과율, 적중 기록)를 만듭니다.
- 영어 발표본을 만듭니다.

## 7. 먼저 정해야 할 것

1. **07 근거가 부족한 기회의 PRD:** 근거 1~2건 기회에도 "가설 포함 초안"을 열지 정해야 합니다.
   - 추천: 열되 모든 R을 H(가설)로 표시하고, "검증 PRD"와 배지로 구분합니다. 2단계의 X1로 데이터가 늘어나면 자연스럽게 검증 PRD가 많아집니다.
2. **20 실시간 폴백:** 스냅샷에 없는 키워드를 검색했을 때 즉석 수집 결과를 보여줄지 정해야 합니다.
   - 추천: 보여주되 서버 인용 검증을 통과한 것만 "미검증 후보"로 보여주고, PRD 근거로는 쓰지 못하게 합니다.
3. **영어 UI 범위:** 세계 대회를 목표로 한다면 시연 동선의 화면 전부를 영어로 지원해야 합니다.
4. **팀 역할:** 3단계(Manyfast)와 2단계(데이터)는 서로 다른 파일을 건드리므로, 동시에 따로 진행할 수 있습니다.
