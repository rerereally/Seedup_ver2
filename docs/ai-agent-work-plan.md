### 확인된 결함

- **경쟁 판단 오류:** "AI 코딩 세션 기억 단절" PRD는 "여러 도구 지원(R4)"을 차별점으로 삼았습니다. 그런데 입력 경쟁 목록의 Cortex, Memex, NeuroTrace가 이미 MCP로 여러 도구를 지원합니다. PRD는 이 셋을 빼고 약한 경쟁 도구(MemoriPilot, Hermes)만 골랐습니다.
- **수요가 아닌 근거:** 직접 만든 사람의 소개 글("I started building…", "I was tired of… ")이 증언으로 들어갔고, 한 사람의 해법이 요구사항(R-02)이 됐습니다.
- **RAG 기준선:** `lib/ingest/rag.ts`의 `MIN_SIMILARITY = 0.35`가 관련 없는 문서의 최고점(약 0.38)보다 낮고, 관련 있는 문서의 최저점(0.25)보다 높습니다.
- **README와 실제가 다름:** README는 글 도우미 챗봇을 RAG라고 소개하지만, `/api/articles/ask`는 벡터 검색 없이 글 본문만 모델에 넘깁니다.
- **채점 모델 불일치:** `scripts/judge-prd.ts`의 기본 채점 모델은 `claude-sonnet-5.5`인데, 성적표에는 무료 nemotron으로 채점했다고 적혀 있습니다.
- **평가 결과 미보관:** `prd-eval.json`이 저장소에 없어 다시 채점할 수 없습니다.

## 1. 원칙

- **에이전트는 찾아 오고, 코드가 채택합니다.** 에이전트가 가져온 인용은 `isVerbatimQuote`와 관련성 판정을 둘 다 통과해야 증언(E-n)이 됩니다.
- **판정, 점수, 증언 채택은 규칙과 코드가 합니다.** 모델에게 넘기지 않습니다.
- **에이전트에는 단계·시간 상한을 둡니다.** 넘거나 실패하면 지금 고정 파이프라인 결과를 그대로 씁니다.
- **에이전트 루프는 네이티브 tool calling 대신 `callJsonModel`로 매 단계 JSON 행동을 받습니다.** 무료 모델에서도 돌아가고 새 의존성이 없습니다.
- **같은 20건으로 비교해 이길 때만 켭니다.**
- **판정 모델은 작성 모델과 다른 회사 모델로 씁니다.**

## 2. P0: 신뢰 (가장 먼저)

### 2-1. 경쟁·근거 조사 에이전트
- **왜:** 경쟁 판단 오류는 신뢰를 깨는 가장 큰 결함입니다. 이 에이전트 하나가 문제 발굴, 검증 리포트, PRD의 경쟁 섹션을 함께 고칩니다.
- **무엇을:** 표현을 바꿔 다시 검색하고, 경쟁 도구 설명과 README를 읽어 우리 차별점과 겹치는지 확인하고, 경쟁 도구 이슈에서 사용자 불만을 모으고, 근거가 기준에 못 미치면 다른 커뮤니티까지 넓힙니다.
- **어디:** `lib/opportunities/report.ts`(`labelRivals`), `lib/opportunities/live-evidence.ts`(`findLiveEvidence`), `lib/opportunities/actors.ts`(`searchSupply`), `lib/opportunities/web.ts`.

- **완료 기준:** 20건 평가셋에서 알려진 직접 경쟁 도구를 놓치는 비율, 근거 수, 걸린 시간, 실패율이 지금보다 나아야 합니다. 실패하면 지금 결과로 돌아가야 합니다.

## 3. P1: PRD 완성도

- [ ] **빈 항목 채우기:** 개발 준비 슬롯, 화면, P0를 항상 채웁니다. 기존 `prd_cache` 7개는 다시 생성합니다.
- [ ] **수락 기준을 테스트로:** 사람의 행동("이어서 진행한다") 대신 실행할 수 있는 확인 방법을 씁니다. 지표에는 측정 방법을 붙입니다.
- [ ] **문장 종류 표시:** 증언 / 사실 / 가설 / 추정으로 나누고, 요구사항마다 근거 강도(원문 3건 이상 / 1~2건 / 없음)를 표시합니다.
- [ ] **차별점 섹션:** 경쟁 도구 사용자의 실제 불만과 "우리만 하는 한 가지"를 씁니다(2-1 결과 사용).
- [ ] **기술 설계와 구현 순서:** 구조, 데이터 모델이나 파일 형식, API·CLI 인터페이스, 스택과 그 이유, 마일스톤, 테스트 계획, 비기능 요구.
- [ ] **고정 뼈대 + 추가 모듈:**
  - 뼈대(항상): 배경, 대상, E→R→F→S, 수락 기준, 6슬롯, 검토 의견.
  - 모듈(LLM이 골라 넣고 고른 이유를 표시): API·개발 도구 / 기업용 / 소비자 앱 / 데이터·AI 제품 / 외부 API 의존.
  - 모듈마다 검사 규칙을 둡니다(예: 기업용이면 권한 항목이 비면 안 됨).
- [ ] **사용자 입력 반박과 방향 제안:**
  - 대상 불일치, 이미 있음, 근거 없는 기능, 범위 과다를 근거 번호와 함께 지적합니다.
  - 다른 방향 2~3개를 원문 수, 경쟁 수와 함께 제안합니다.
  - 위치: 질문 단계(`lib/opportunities/questions.ts`)와 PRD "검토 의견" 섹션.
  - 결정은 사용자가 합니다. 그대로 가면 가설(H-n)로 표시합니다.
- [ ] **보강 에이전트:** 초안 뒤에 빈 곳 찾기 → 조사(의존 API 가격·약관, 경쟁 약점, 스택, 반대 근거) → 사용자만 정할 것은 질문 → 출처와 종류 표시를 붙여 채우기.
- [ ] **대상별 출력:** 같은 PRD를 개발자용, 바이브코더용(스택 하나로 확정, 단계별 프롬프트, 배포·비용, 개발을 몰라도 확인하는 방법), 기업용으로 내보냅니다.
- [ ] **저장소 기반 슬롯 채우기:** 내 저장소를 읽어 권한, 데이터 구조, 오류 처리를 채웁니다(`/prd/repo`와 연결).

## 6. P2: 공유와 협업

현재: `shared`를 켜면 `/spec/[id]`가 읽기 전용으로 보이고, 대화로 고치기(`/api/opportunities/prd/revise`)가 있습니다. 버전 기록은 브라우저에만 남습니다.

1. [ ] **공개 목록:** 공개 범위 3단계(비공개 / 링크 / 전체), 기본값은 비공개. 문제별로 묶어 "이 문제로 PRD N개, M개는 만들어짐"을 보여 주고, 이 수치를 평가의 공급 신호로 씁니다. 포크를 지원하고, 근거 기준을 통과한 PRD를 위에 올리며, 신고 기능을 둡니다. 빈 화면을 피하려고 2-1 수정 뒤의 공개 PRD 7개로 시작합니다.
2. [ ] **서버 버전 기록과 항목별 댓글:** 버전을 브라우저에서 DB로 옮기고, R-n/F-n마다 댓글을 답니다.
3. [ ] **팀 편집:** 링크는 보기만 되고, 편집은 로그인한 초대 멤버만 합니다. 권한은 보기 / 댓글 / 편집 3단계입니다. 실시간 동시 편집은 만들지 않고, 저장할 때 버전을 확인합니다. 증언은 잠그고 추가만 허용합니다. PRD가 바뀌면 MCP에 "다시 확인 필요"를 표시합니다.
4. [ ] **수정 에이전트:** "R-03이 너무 크다" 같은 말을 알아듣고 바뀌는 부분을 제안합니다. 영향 받는 F/S/E를 보여 주고, 승인과 거절을 받으며, 필요하면 조사와 반박을 합니다. 팀에서는 제안으로 올립니다.
