# Seedup 수정·개선 목록, 메인 기능, 세계 해커톤 전략

작성일 2026-11-16. `seedup-evaluation-strategy.md`의 평가를 실행 계획으로 옮긴 문서입니다. 근거가 되는 코드 위치와 데이터는 그 문서에 있습니다.

판단의 한계는 같습니다. 배포 사이트와 운영 DB를 보지 않았고, 어떤 세계 해커톤에 나갈지 정해지지 않아 규정을 확인하지 못했습니다.

## 1. 한 줄 결론

**메인 기능은 "원문을 가리키는 스펙" 하나로 정하고, 나머지는 숨기거나 미룹니다.** 고칠 것은 새 기능보다 데이터, 주장의 정확성, 데모 안정성이 먼저입니다.

## 2. 메인 기능

### 2.1 무엇을 메인으로 할 것인가

**실제 사람이 쓴 불만 원문에서 출발해, 모든 요구사항이 그 원문을 가리키는 스펙을 만들고, 코딩 에이전트에 넘기는 한 줄기**입니다.

화면으로는 다음 네 단계입니다.

1. 홈에서 불만 원문 칩을 모읍니다.
2. 근거 확인서가 기준(증언 3건, 플랫폼 2종) 통과 여부를 보여줍니다.
3. `/prd`에서 요구사항을 누르면 원문이 강조되고, 근거 없는 항목은 가설로 분리됩니다.
4. MCP나 내보내기로 코딩 에이전트에 전달합니다.

이것을 메인으로 고르는 이유는 세 가지입니다.

- Seedup에서 다른 서비스가 하지 않는 유일한 부분입니다. 모델이 초안을 쓰고 서버가 판정하는 구조가 코드로 강제되어 있습니다.
- 3분 안에 한 장면으로 보여줄 수 있습니다.
- 이미 끝까지 구현되어 있어, 새로 만들 것이 아니라 다듬을 것만 남았습니다.

### 2.2 기능별 처리

| 기능 | 처리 | 이유 |
|---|---|---|
| 홈 증언 칩과 근거 확인서 | **메인** | 서비스가 하는 일을 설명 없이 보여줌 |
| 스펙 작업 화면(`/prd`) | **메인** | 핵심 장면 |
| MCP 서버와 에이전트 지침 내보내기 | **메인** | 스펙이 문서로 끝나지 않고 실행으로 이어짐 |
| 기회 목록과 상세 | 유지 | 메인으로 들어가는 입구 |
| 공유 링크(`/spec/[id]`) | 유지 | 심사위원이 직접 열어 볼 수 있음 |
| 내 씨앗과 역기획 | 유지, 발표에서는 한 문장 | 두 번째 사용 사례. 시연 동선에는 넣지 않음 |
| 보관함 | 유지 | 메인의 저장소 |
| 아이디어 평가 | 숨김 | 핵심 주장과 다른 이야기 |
| 뉴스, 논문 리뷰, 글 도우미 | 숨김 | "이건 왜 있나" 공격 대상 |
| 트렌드, 오픈소스, AI 제품, 프로젝트 | 숨김 | 같은 이유 |
| 추천, 뉴스레터 | 숨김 | 같은 이유 |

숨김은 삭제가 아닙니다. `components/Header.tsx`의 `PRIMARY`와 `MORE` 목록에서 빼서 메뉴에만 안 보이게 합니다. 코드와 주소는 그대로 둡니다.

### 2.3 메인에 덧붙일 것 하나

기능을 하나만 추가한다면 **증언이 요구사항을 실제로 뒷받침하는지 확인하는 검사**입니다.

- **지금의 구멍:** 요구사항이 어떤 증언을 인용할지는 모델이 고르고, 서버는 그 번호가 존재하는지만 확인합니다. 무관한 증언을 인용해도 통과합니다.
- **하는 일:** 요구사항과 인용된 원문을 짝지어 "이 원문이 이 요구사항을 뒷받침하는가"를 한 번 더 판정하고, 아니면 가설로 내립니다. 엔진이 이미 증언에 대해 같은 방식의 재검사를 하고 있어(`engine.ts`의 최종 관련성 검사) 같은 패턴을 스펙에 적용하면 됩니다.
- **효과:** "모든 요구사항이 검증됐다"고 말할 수 있게 됩니다. 지금은 그렇게 말하면 과장입니다.

`final-report.md`가 제안한 "PR을 스펙의 완료 기준과 비교해 코멘트 달기"는 그다음 후보입니다. 근거에서 코드까지 이어지는 그림을 완성하지만 작업량이 크므로, 3절의 필수 항목이 끝난 뒤에만 시작합니다.

### 3.3 나중에 할 것

- 비개발자 불만 소스 추가. 수집 필터와 프롬프트 두 곳, 공급 조사 채널까지 바꿔야 하는 중간 크기 작업입니다.
- PR과 스펙 완료 기준 비교.
- 프로필과 관리자 화면의 디자인 통일.
- 공유 링크 QR 코드.
- 한국·일본 커뮤니티 수집원.

### 3.4 하지 않을 것

- 인터뷰 기록 관리, 지켜보기 알림.
- 화면 전체 디자인 개편.
- 실시간 공동 편집, 와이어프레임 이미지 생성.
- 숨긴 기능의 개선 작업.

## 4. 세계 해커톤 전략

### 4.1 국내 주관사 해커톤과 다른 점

국내 데모데이 심사위원은 "정말 필요한가"와 현장에서 나온 참신함을 물었습니다. 세계 규모 해커톤은 성격이 다를 가능성이 높습니다. 아래는 일반적인 경향에 대한 제 판단이고, 대회마다 다르므로 공지를 확인해야 합니다.

| 항목 | 국내 주관사 해커톤 | 세계 해커톤(일반적 경향) |
|---|---|---|
| 심사위원 | 창업·사업 관점 | 개발자, 기술 회사 소속이 많음 |
| 개발자 도구 주제 | 감점 요인이 될 수 있음 | 불리하지 않음. 코딩 에이전트 관련 주제는 오히려 관심이 큼 |
| 평가 방식 | 현장 발표 | 영상과 저장소로 먼저 걸러지는 경우가 많음 |
| 언어 | 한국어 | 영어 |
| 규정 | 미정 | 기간 내 신규 개발분만 인정하는 대회가 많음 |

따라서 **Seedup은 국내 주관사 해커톤보다 세계 해커톤에 더 잘 맞는 프로젝트**라고 봅니다. 국내에서 약점이던 "개발자를 위한 도구"가 세계 무대에서는 약점이 아닙니다.

### 4.2 포지셔닝

한 문장은 이렇게 씁니다.

> **Coding agents build fast. Seedup makes sure they build the right thing: every requirement points to a real developer's own words, and anything without a source is marked as a hypothesis.**

- 경쟁 구도는 기획서 작성 도구가 아니라 "코딩 에이전트에게 무엇을 시킬지 정하는 단계"로 잡습니다.
- 강조할 것은 생성이 아니라 검증입니다. "AI가 쓴 것을 서버가 걸러낸다"는 점이 기술적 깊이로 평가받습니다.
- MCP 서버는 세계 무대에서 더 큰 강점입니다. 터미널에서 실제로 동작하는 장면을 보여줍니다.

### 4.3 대회 고르기와 규정 확인

- **기존 코드 허용 여부를 가장 먼저 확인합니다.** 허용하지 않는 대회라면 Seedup 전체가 아니라 기간 안에 새로 만든 부분만 출품해야 합니다. 이 경우 2.3절의 뒷받침 검사나 PR 비교 기능을 그 기간에 만드는 것으로 계획합니다.
- 주최사가 특정 기술 사용을 요구하는지 확인합니다. 모델 호출은 `lib/opportunities/llm.ts`와 `lib/ingest/ai.ts` 두 곳, 임베딩은 `lib/ingest/rag.ts` 한 곳이라 교체 범위가 좁습니다.
- 주제가 맞는 대회를 고릅니다. 개발자 도구, AI 에이전트, MCP를 다루는 대회가 가장 잘 맞습니다.

### 4.4 제출물

세계 해커톤은 발표장에 서기 전에 제출물로 평가받는 경우가 많습니다.

| 제출물 | 기준 |
|---|---|
| 데모 영상 | 2~3분. 첫 15초 안에 결과 화면. 영어 자막 또는 영어 음성 |
| 저장소 README | 영어. 맨 위에 한 문장 소개, 데모 GIF, 접속 링크. 지금의 한국어 README는 별도 파일로 |
| 접속 가능한 데모 | 로그인 없이 핵심 장면을 볼 수 있는 링크. 공유 링크(`/spec/[id]`)를 예시로 고정 |
| 설명 글 | 문제, 접근, 만든 것, 어려웠던 점, 다음 단계. 대회 양식에 맞춤 |

### 4.5 영상 구성

| 시간 | 내용 |
|---|---|
| 0:00~0:15 | 코딩 에이전트가 그럴듯하지만 아무도 원하지 않는 기능을 만드는 장면 |
| 0:15~0:40 | 홈에서 실제 불만 원문을 모으고 근거 확인서가 통과되는 장면 |
| 0:40~1:20 | 스펙 화면. 요구사항을 누르면 원문이 강조되고, 근거 없는 항목이 가설로 떨어짐 |
| 1:20~2:00 | 터미널에서 MCP로 스펙을 받아 에이전트가 첫 기능을 구현 |
| 2:00~2:30 | 숫자. 채택한 인용과 걸러낸 인용, 기준 통과 기회 수 |
| 2:30~2:45 | 한 문장 마무리와 접속 링크 |

### 4.6 세계 무대에서 받을 질문

| 질문 | 답 |
|---|---|
| 불만 수집 서비스는 이미 있지 않나 | 수집은 같습니다. 인용을 원문과 대조하고, 근거 없는 요구사항을 분리하고, 에이전트에 직접 넘기는 데까지 가는 점이 다릅니다 |
| 원문 대조는 무엇을 보장하나 | 인용이 원문에 실재함을 보장합니다. 관련성은 별도의 재검사로 거릅니다 |
| 데이터가 얼마나 되나 | 3.1의 1번을 마친 뒤의 실제 숫자로 답합니다. 부풀리지 않습니다 |
| 공개 게시글 사용은 괜찮나 | 공식 API로 수집하고 원문 링크를 함께 겁니다. 각 플랫폼 약관은 제출 전에 다시 확인합니다 |
| 왜 무료 모델인가 | 비용 없이 매일 돌리기 위해서였고, 검증을 서버가 하므로 모델이 약해도 지어낸 근거는 통과하지 못합니다 |

### 4.7 순서

1. 3.1의 1~7번을 끝냅니다. 여기까지가 어떤 대회에도 필요한 기본입니다.
2. 3.1의 8번 사례를 만듭니다.
3. 나갈 대회를 정하고 규정을 확인합니다.
4. 영어 README와 영상을 만듭니다. 3.2의 11, 12번을 함께 합니다.
5. 남는 시간에 2.3절의 뒷받침 검사를 추가합니다.
6. 제출 전날 시연 동선을 세 번 연속 성공시키고 영상을 다시 확인합니다.

## 5. 확인하지 못한 것

- 운영 DB의 현재 기회 수와 배포 사이트 동작.
- 출전할 세계 해커톤과 그 규정. 4.1절의 경향은 일반론입니다.
- 경쟁 서비스의 실제 기능.
- 각 수집 플랫폼의 약관.
