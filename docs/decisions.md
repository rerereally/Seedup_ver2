# 결정 기록

팀(2인)과 에이전트가 함께 보는 결정 목록입니다. 새 결정은 맨 위에 추가하고, 지난 결정을 뒤집을 때는 지우지 말고 새 항목에 "뒤집음: <이전 제목>"을 적습니다. 계획에 영향을 주는 결정은 [`supervisor-plan.md`](supervisor-plan.md)를 먼저 고친 뒤 여기에 남깁니다(계획 세션에서만).

형식:

```
## YYYY-MM-DD 결정 제목
- 결정:
- 이유:
- 버린 대안:
- 누가: 사람 이름 / 에이전트(도구, 세션)
```

## 2026-11-20 공개 slug 프로젝트 키는 실제 기회인지 확인한다

- 결정: 프로젝트 키가 공개 `<slug>`이면 형식뿐 아니라 실제로 있는 기회인지 `getOpportunity`로 확인하고, 없으면 404로 답한다(계획 3-3).
- 이유: 오타나 지어낸 slug로 빈 프로젝트 · 목표가 쌓이는 것을 막는다.
- 버린 대안: 형식만 확인(행이 사용자별이라 보안 문제는 없지만 쓰레기 데이터가 생김).
- 누가: 장차희(계획 세션), PR #131 검토 중 결정

## 2026-11-20 규칙을 바꾸려면 문서를 먼저 바꾼다

- 결정: 규약 · 규칙 · 계획은 `CONTRIBUTING.md`나 `docs/supervisor-plan.md`를 고치는 PR이 머지된 뒤부터 적용한다. 대화나 에이전트 메모리로만 정한 규칙은 효력이 없다.
- 이유: 두 사람과 여러 에이전트가 같은 규칙을 보려면 저장소 문서가 유일한 기준이어야 한다.
- 버린 대안: 대화로 정하고 나중에 문서에 반영하기.
- 누가: 계획 세션(장차희)

## 2026-11-20 문서는 고치는 쪽을 나눈다

- 결정: 계획 · 결정 문서는 계획 세션만, `status.md`는 PR을 머지한 사람이 머지 직후 고친다. 실행 세션은 PR 본문에 진행과 status 반영 줄을 적는다(`CONTRIBUTING.md` 8절).
- 이유: 여러 세션이 같은 문서를 동시에 고치면 충돌한다.
- 버린 대안: 각 실행 PR이 status.md를 직접 고치기.
- 누가: 계획 세션(장차희)

## 2026-11-20 승인은 터미널 대화에서

- 이유: 사용자가 머무는 곳이 터미널이라 승인 흐름이 끊기지 않는다.
- 버린 대안: 대시보드에서 승인 버튼으로 받기.

## 2026-11-20 완료 검증은 2단

- 결정: 1단은 로컬 훅이 커밋 전에 즉시 예방(🔵 로컬 확인), 2단은 push 뒤 서버가 GitHub의 실제 SHA · CI로 확정(🟢 감독관 검증). 서버 검증은 자료를 먼저 모으고 모델 1~2회 호출하는 단순형.
- 이유: 에이전트가 보낸 diff와 로컬 훅은 우회될 수 있고, 모델이 도구를 골라 읽는 루프는 시간과 구현이 크다.
- 버린 대안: tool calling 검증 루프, 사용자 저장소의 GitHub Actions 안에서 판정.
- 누가: 계획 세션(장차희)
